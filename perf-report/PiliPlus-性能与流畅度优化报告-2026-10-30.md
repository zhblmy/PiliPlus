# PiliPlus 性能与流畅度优化报告

## 一、可修复的错误

### 2.1 弹幕被整批丢弃（优先级 P0，1 行修复）

- **位置：** [`lib/pages/danmaku/view.dart:120`](../lib/pages/danmaku/view.dart:120)
- **代码：**

```dart
for (DanmakuElem e in currentDanmakuList) {
  if (e.weight < danmakuWeight) return;   // ← 应为 continue
  ...
  _controller!.addDanmaku(...);
}
```

- **问题：** 这里是 100ms 时间片内的弹幕批次循环，`return` 会直接结束整个 `videoPositionListen` 回调。批次里只要出现一条低权重弹幕，**后面同批次的弹幕全部不再显示**。
- **用户可见影响：** 开启"弹幕权重过滤"后，弹幕肉眼可见地变少，且变少的量与被过滤弹幕在批次中的位置有关（越靠前丢得越多），看起来像随机丢失，很难排查。
- **修法：** `return` → `continue`。
- **验证：** 同一条视频，开关"权重过滤"对比弹幕条数；或在 `addDanmaku` 处统计调用次数。

### 2.2 分页状态卡死（优先级 P0）

- **位置：** [`lib/pages/common/common_list_controller.dart:23`](../lib/pages/common/common_list_controller.dart:23)
- **代码结构：**

```dart
Future<void> queryData([bool isRefresh = true]) async {
  if (isLoading || (!isRefresh && isEnd)) return;
  isLoading = true;
  final LoadingState<R> res = await customGetData();   // ← 抛异常则下面全部不执行
  ...
  isLoading = false;   // 只在正常路径复位
}
```

- **问题：** 没有 `try/finally`。`customGetData()`（网络异常、`Success` 分支里的 `getDataList` / `handleListResponse` / `loadingState` 赋值）抛出任何异常，`isLoading` 会永久停留在 `true`。
- **用户可见影响：** 之后每一次下拉刷新、触底加载都会在 `if (isLoading ...) return;` 处直接返回——**页面"假死"，只能退出重进**。`CommonListController` 被几乎所有列表页继承，影响面很大。
- **修法：** 用 `try { ... } finally { isLoading = false; }`；同时按项目既有约定显式处理异常（`loadingState.value = Error(...)` 或日志上报），不要只复位状态而隐藏故障。
- **参照：** 同仓的 [`lib/pages/video/controller.dart:841`](../lib/pages/video/controller.dart:841) 的 `queryVideoUrl()` 就是正确写法（`isQuerying` + `try/finally`），可照搬该模式。

### 2.3 清除缓存"假成功"（优先级 P0）

- **位置：** [`lib/utils/cache_manager.dart:52`](../lib/utils/cache_manager.dart:52)、[`lib/pages/about/view.dart:216`](../lib/pages/about/view.dart:216)
- **问题：** `clearLibraryCache()` 内部 `catch (_) {}` 吞掉所有异常后正常返回；设置页 `await` 返回后无条件 `SmartDialog.showToast('清除成功')`，因此"失败"与"成功"走到同一个提示；页面外层 `try/catch` 的失败分支永远进不去。
- **修法：** 二选一
  1. 让异常继续抛出（删掉 `catch` 或 `rethrow`）；
  2. 返回 `bool` / 结果对象，仅在成功时提示"清除成功"，失败时按现有错误反馈方式提示。

### 2.4 缓存统计误报 0（优先级 P1）

- **位置：** [`lib/utils/cache_manager.dart:19`](../lib/utils/cache_manager.dart:19)
- **问题：** `loadApplicationCache()` 捕获异常后 `return 0`；目录遍历异常被忽略；单个文件 `lengthSync()` 失败时 [`_fileSize`](../lib/utils/cache_manager.dart:105) 也返回 0。调用方 [`lib/pages/about/view.dart:63`](../lib/pages/about/view.dart:63) 直接格式化显示，无法区分"真的没有缓存""统计失败""部分统计"。
- **修法：** 返回 `int?`（失败为 `null`）或 `(bytes, isComplete)`；页面失败时显示"无法获取"或保留上次有效值。

### 2.5 build 期间触发分页（优先级 P1）

- **位置：** [`lib/pages/rcmd/view.dart:87`](../lib/pages/rcmd/view.dart:87)、[`lib/pages/dynamics_tab/view.dart:101`](../lib/pages/dynamics_tab/view.dart:101)
- **代码：**

```dart
itemBuilder: (context, index) {
  if (index == response.length - 1) controller.onLoadMore();
  ...
}
```

- **问题：** 在 `itemBuilder`（布局阶段的构建）里发网络请求属于副作用。正常情况下靠 `isLoading` 守卫没问题，但与 2.2 叠加后风险放大：`isLoading` 一旦卡住，这里会在每次重建时重复触发；列表等内容不足一屏时也会每帧重复调用。
- **修法：** 移到滚动通知（接近底部时触发）或 `WidgetsBinding.instance.addPostFrameCallback`；同时保证请求入口自身有幂等守卫。

### 2.6 图片网格恒重建（优先级 P2）

- **位置：** [`lib/common/widgets/image_grid/image_grid_builder.dart:67`](../lib/common/widgets/image_grid/image_grid_builder.dart:67)
- **问题：** `bool updateShouldRebuild(ImageGridBuilder oldWidget) => true;`，父级任何 rebuild 都会让 Element 标记需要重建并 `scheduleLayoutCallback()`，重新跑一遍子项 builder。
- **修法：** 按"会影响布局结果的配置"比较后再返回（图片列表可能原地修改，不能只比较列表对象身份；同时要覆盖 builder、交互回调等配置变化）。改之前先确认哪些父级会高频 rebuild 这个网格。

## 三、性能优化项

每条包含：位置 → 现状 → 建议 → 预期效果（含验证指标）。

### B1. 视频页"收起顶栏"每帧重建 + 每帧 saveLayer（收益最高）

- **位置：**
  - [`lib/pages/video/view.dart:678`](../lib/pages/video/view.dart:678)：`Opacity(opacity: videoDetailController.scrollRatio.value, ...)`
  - [`lib/pages/video/view.dart:754`](../lib/pages/video/view.dart:754)：`Obx(() { final scrollRatio = ...; return Positioned.fill(... _buildOverlayToolBar(scrollRatio)); })`
  - [`lib/pages/video/view.dart:539`](../lib/pages/video/view.dart:539)：`Obx` 里用 `Color.lerp(..., scrollRatio)` 计算状态栏底色
  - 驱动源：[`lib/common/widgets/sliver/video_header.dart:53`](../lib/common/widgets/sliver/video_header.dart:53)（`performLayout` 中 `addPostFrameCallback` → 写 `RxDouble`）
- **现状：** 播放器头部收起时，`scrollRatio` 每帧变化 → 每帧触发一次 `Obx` 重建（含多个 `IconButton`、`Stack`、`Container`）；同时 `Opacity` 在 0&lt;opacity&lt;1 区间会给这一层加 `saveLayer`，等于每帧一次离屏合成。此外 `addPostFrameCallback` 写入 → 下一帧才重建，形成"每帧一次延后重建"的固定节奏。
- **建议：**
  1. 把 `scrollRatio` 换成 `ValueNotifier<double>`，只给"真正需要随比例变化的绘制属性"用 `ValueListenableBuilder`/`AnimatedBuilder`；
  2. 透明度交给合成层（`FadeTransition`）或直接把 alpha 写进 `Container`/文字颜色，避免 `Opacity` 的 `saveLayer`；
  3. 工具栏子树（按钮组）移出 `Obx`，不要每帧重建；
  4. 状态栏底色只在跨越阈值（例如 0 / 0.5 / 1）时切换，而不是连续 lerp。
- **预期：** 视频页下滑收起时 `build` 与 `raster` 峰值下降；用 DevTools Performance 录制"进入视频页 → 上滑收起 → 下滑展开"，对比 `frame build time` 直方图与最长帧。功能行为不变。

### B2. 列表体被单个 `Obx` 包住，翻页时整屏重建

- **位置：** [`lib/pages/rcmd/view.dart:56`](../lib/pages/rcmd/view.dart:56)、[`lib/pages/dynamics_tab/view.dart:64`](../lib/pages/dynamics_tab/view.dart:64)
- **现状：**

```dart
sliver: Obx(() => _buildBody(colorScheme, controller.loadingState.value)),
```

每次 `loadingState.refresh()`（每追加一页都会调用）都会重建整个 sliver，生成新的 `SliverChildBuilderDelegate`（其 `shouldRebuild` 恒为 `true`），于是**所有可见 item 全部重建**——包含 `VideoCardV` 里的 `Card / InkWell / LayoutBuilder / NetworkImgLayer`。

- **建议：**
  1. `Obx` 只负责 Loading / Error / Success 三种分支切换；
  2. 列表本体用独立 sliver，翻页时只让新增项构建（数据放进 `ValueListenable`/`GetBuilder` 的独立范围，或使用支持局部更新的列表封装）；
  3. 对 item 根节点加 `RepaintBoundary`，至少把重建限制在 build 阶段而不牵连重绘。
- **预期：** 翻页那一帧不再整屏重建；用 DevTools 对比"连续翻 3 页"的最长帧与 jank 数量。

### B3. 玻璃栏 BackdropFilter 每帧重算

- **位置：** [`lib/common/widgets/liquid_glass.dart:103`](../lib/common/widgets/liquid_glass.dart:103)（`ImageFilter.blur(sigmaX: blur, sigmaY: blur)`）
- **参数：** 底栏 [`lib/pages/main/view.dart:39`](../lib/pages/main/view.dart:39) `_kBottomNavBlur = 28.0`；首页顶栏 [`lib/pages/home/view.dart:286`](../lib/pages/home/view.dart:286) `blur: 16`
- **现状：** 玻璃条覆盖在列表之上，列表每帧滚动 → 下方内容每帧变化 → 每帧都要对该区域重新做高斯模糊；竖屏时顶栏与底栏同时存在是两层 backdrop。
- **建议（按代价从低到高）：**
  1. σ 28 → 12\~16（视觉差异很小，GPU 成本随 σ 明显下降）；
  2. 滚动进行中降级为接近不透明的纯色，滚动停止后再恢复模糊（监听 `ScrollStartNotification` / `ScrollEndNotification` 做状态切换）；
  3. 增加"性能模式/减少特效"开关，低端机与高刷大屏默认关闭模糊。
- **预期：** raster 线程耗时下降，120Hz + 高分屏最明显；验证指标为同场景滚动时的 `raster` 平均/峰值与掉帧数。

### B4. 首帧前仍可后移的等待

- **位置：** [`lib/main.dart:114`](../lib/main.dart:114) `await _initAppPath();`（随后 [`main.dart:135`](../lib/main.dart:135) 才在 `Future.wait` 里并行 `_initTmpPath()`）；[`lib/main.dart:140`](../lib/main.dart:140) `MemoryBudget.init()`；[`lib/main.dart:124`](../lib/main.dart:124) + [:142](../lib/main.dart:142) 冷 Box（`historyWord` / `video` / `watchProgress` / `reply`）
- **现状：**

# **首页代码检查结论**

### **1. `_showTopBarRequest` 可能会把用户手动收起的顶栏弹出来（重要）**

dart

```
return Obx(() {
  if (showTopBar.value &&
      _barCollapse.value > 0.0 &&
      !_barAnim.isAnimating) {
    WidgetsBinding.instance.addPostFrameCallback((_) {
      if (mounted) _animateBar(false);
    });
  }
  return const SizedBox.shrink();
});
```

问题：

- `Obx` 只跟踪 `showTopBar.value`（GetX 的 Rx），**不跟踪** *`barCollapse` **和*** `barAnim.isAnimating`（它们是普通对象）。
- 而 `showTopBar` 在 `HomeController.onInit` 里被初始化为 `RxBool(true)`，之后几乎不会变 false。`Obx` 不会因 `showTopBar` 变化而重建，但每次 [`HomePage.build`](http://HomePage.build) 时父级传入新的 `Obx` widget，State 会重新执行 builder。
- 于是：用户在即时模式上滑收起顶栏（`_barCollapse > 0`），之后任何触发 [`HomePage.build`](http://HomePage.build) 的事件（键盘弹出/收起、旋转屏幕、主题变化、系统字号变化等）都会让这段逻辑命中，**自动把顶栏展开**。

建议：不要在 build 里做「检查并触发」，改用 `ever` 监听 `showTopBar` 的变化，只在 false→true 时响应：

dart

```
Worker? _showTopBarWorker;

@override
void initState() {
  super.initState();
  // ...
  final showTopBar = _homeController.showTopBar;
  if (showTopBar != null) {
    _showTopBarWorker = ever<bool>(showTopBar, (value) {
      if (value && _barAnim.value > 0 && !_barAnim.isAnimating) {
        _animateBar(false);
      }
    });
  }
}

@override
void dispose() {
  _showTopBarWorker?.dispose();
  // ...
}
```

同时需要确认 `MainController.setSearchBar()` 是否真的会产生 false→true 的变化（如果它只是 `showTopBar.value = true`，而初始就是 true，`ever` 也不会触发）。稳妥做法是把 `showTopBar` 改成 `RxInt` 计数器（`setSearchBar` 自增），或 `setSearchBar` 先置 false 再置 true。



# **动态页代码检查结论（修订版）**

### **1. 请求异常导致 isLoading 卡死（优先级最高）**

**问题说明：**  
两个基类都先将 `isLoading` 设为 true，然后 `await customGetData()`；若请求本身或后续响应处理抛异常，就会跳过重置步骤，导致后续 `loadMore`、`refresh` 被永久挡住。`CommonListController` 的空列表分支虽会主动复位，但不能覆盖异常路径。

**位置：**  
`CommonDataController` 与 `CommonListController` 的请求入口。

**关键区分：**  
`finally` 只能确保解锁，不能捕获异常，也不能让页面显示错误。这里实际上是两件事，应分别决策，不要混成一个隐式变化：

- 若希望保留异常冒泡行为，用 `try/finally`，只保证 `isLoading` 一定复位。
- 若希望统一转成 UI 错误状态，则需要显式 `catch` 并更新 `loadingState`（置为 Error 或保留旧数据 + 记录错误）。

**风险：**  
跨调用方改动，影响面最大。需要先确认现有调用方是否依赖“异常直接冒泡”。

**预期收益：**  
最高。一处修复覆盖 `onInit`、`onRefresh`、`onSelectUp`、`_buildUpPanel.onReload` 等全部路径，消除“请求失败后状态卡死”的整类故障。

### **2. onChangeAccount 忽略 isLogin**

**问题说明：**  
`onChangeAccount(bool isLogin)` 当前直接执行 `onReload()`，没有区分登录态。登出后 `customGetData()` 仍会走 `followUp()` 或 `followings(vmid: Accounts.main.mid)`，mid 可能无效。

需要修正此前过强的表述：

- `onReload()` 会先把状态改成 Loading，通常会清掉旧内容再请求，**不是**简单“停留在旧列表”。
- 接口是否失败取决于服务端响应，不能仅凭“mid 无效”断言“必然失败”。

**额外风险：**  
账号登录/切换时也可能通过 `isLogin.refresh()` 通知监听器。`isLogin` 只能区分登录与登出，**无法识别“换了哪个账号”**。如果修登出逻辑，除了清空状态，还应考虑：登出前启动的请求稍后完成、重新写回旧账号数据的竞态。

**位置：**  
`DynamicsController.onChangeAccount`。

**改动量：**  
小到中等（若处理竞态则中等）。

**风险：**  
低到中。

**预期收益：**  
真实行为修复。登出后不再用无效身份发请求，并避免旧账号数据被异步回写。

---

### **3. initialIndex 越界**

**问题说明：**  
`TabController` 初始化直接传入 `Pref.defaultDynamicTypeIndex`，Pref 脏数据或旧版本枚举长度不匹配时可能越界触发 assert。

**两个细节：**

- Dart 的 `clamp()` 返回 `num`，传给需要 `int` 的 `initialIndex` 时应显式 `.toInt()`。
- 钳制到最后一个 Tab 只是一种策略；若异常配置应回退到默认 Tab（当前是 all），也可以显式选默认值。两种策略需要明确选一种。

**位置：**  
`DynamicsController.onInit` 创建 `TabController` 处。

**改动量：**  
一到两行。

**风险：**  
零。

**预期收益：**  
防启动阶段因 Pref 脏数据崩溃。

---

### **4. \_jumpToTab 硬编码 Tab 索引**

**问题说明：**  
`_jumpToTab` 中写死 `tabController.index = mid == -1 ? 0 : 4;`。当前 `0` 对应 `all`，`4` 对应 `up`。枚举顺序调整后会跳错或越界。

**修正此前注释：**  
应使用 `DynamicsTabType.all.index` 和 `DynamicsTabType.up.index`，而不是 `following`——当前枚举没有 `following` 这个值。

**位置：**  
`DynamicsController._jumpToTab`。

**改动量：**  
一行。

**风险：**  
零。

**预期收益：**  
低成本防回归。当前无立即 bug。

`_onScrollNotification` 先确认通知属于当前列表，再使用该通知的 `metrics`；两者是同一个 Scrollable 的位置语义。改成 `position.pixels` 可能更直观，但不解决已确认问题。

# **视频详情页代码 Review —— 问题清单**

范围：`pages/video/controller.dart`、`pages/video/view.dart`，关联 `download_panel/view.dart`、`pl_player/models/data_source.dart`、`widgets/header_control.dart`。仅列经代码核对成立的项，按优先级排列。

---

## **P1**

### **P1-1 `updatePlayer` 缺 `data.dash` 判空**

- **位置**：`controller.dart` `updatePlayer` → `findVideoByQa` → `data.dash!.video!`
- **问题**：durl 兜底路径下 `data.dash == null` 但 `currentVideoQa` 被设为非空；`updatePlayer` 未判 `dash` 即调用 `findVideoByQa`，后者强解包 `data.dash!`。画质/音质选择入口有前置保护，但解码格式切换等路径可调到此函数。
- **改法**：`updatePlayer` 开头加 `if (currentVideoQa == null || data.dash == null) return;`。

### **P1-2 `findVideoByQa` 可空化**

- **位置**：`controller.dart` `findVideoByQa`
- **问题**：`data.dash!.video!` 强解包；`videoList` 为空时 `videoList.first` 抛 `Bad state: No element`。正常 DASH 路径由 `findAvailableVideoQuality` 保证 qa 存在，但状态残留（切视频后旧 qa 保留、新数据不含该 qa）或 durl 路径下会触发。
- **改法**：返回 `VideoItem?`，`data.dash?.video?.where(...) ?? const []`，空列表返回 null；`updatePlayer` 判空后回退 `data.findAvailableVideoQuality(...)` 或 toast。

### **P1-3 `PageStorageKey(CommonIntroController)` 复用冲突**

- **位置**：`view.dart` `videoIntro` 内 `CustomScrollView`、`localIntroPanel` 内、`_childWhenDisabledLandscapeInner` 右侧 related 的 `CustomScrollView`
- **问题**：三处使用同一个 `PageStorageKey(CommonIntroController)`。横向布局下左侧 `videoIntro(needRelated: false, needCtr: false)` 与右侧 related 滚动视图同时挂载（`Offstage` 不销毁子树），同一 `PageStorageBucket` 下同 key 槽位互相覆盖滚动位置。
- **改法**：按用途拆分并带 `heroTag` 隔离：`PageStorageKey('videoIntro_$heroTag')`、`PageStorageKey('related_$heroTag')`、`PageStorageKey('localIntro_$heroTag')`。

### **P1-4 `buildItem` / `onSkipSegment` 用 `indexOf` 定位**

- **位置**：`controller.dart` `buildItem`（多处 `listData.indexOf(item)`）、`onSkipSegment`
- **问题**：`AnimatedList.itemBuilder` 已提供 index，但 `buildItem(Object item, Animation<double> animation)` 签名未接，view 侧 `itemBuilder: (context, index, animation)` 丢弃 index，退化为线性查找；重复元素时可能定位到错误项（列表插入有 `contains` 检查，风险有限但可避免）。
- **改法**：`buildItem` 增加 `int? listIndex` 参数，view 侧传 `listIndex: index`；`onSkipSegment` 用 `listData.length - 1`。⚠️ `item is int` 分支里 `pages![item]` 的 `item` 是分 P 下标，命名需区分（`listIndex` / `partIndex`）。

### **P1-5 `currentAudioQa` 加载路径未清除 + `updatePlayer` 音频强解包**

- **位置**：`controller.dart` `_queryVideoUrl` 音频为空分支、`updatePlayer`
- **问题**：`_queryVideoUrl` 在音频为空时只清 `audioUrl`，未清 `currentAudioQa`，旧值残留。切到无音轨视频后再触发 `updatePlayer`（如解码格式切换），进入 `if (currentAudioQa != null)` 分支，`data.dash!.audio!` 强解包崩溃。
- **改法**：
  - `_queryVideoUrl` 音频为空分支补 `currentAudioQa = null`；
  - `updatePlayer` 改为 `final audioList = data.dash?.audio; if (currentAudioQa != null && audioList != null && audioList.isNotEmpty) { ... } else { audioUrl = ''; currentAudioQa = null; }`。

### **P1-6 离线 `entry.typeTag!` 契约**

- **位置**：`controller.dart` `playerInit` 的 `FileSource(typeTag: entry.typeTag!)`；`initFileSource` 从 `args['entry']` 取
- **问题**：`typeTag` 模型字段可空但强解包，`entry` 由下载服务构造经 `args` 传入，属外部输入。`assert` 在 release 不生效；用 `'unknown'` 拼接路径会把"数据无效"变成"文件找不到"，掩盖问题。
- **改法**：`initFileSource` 入口运行时校验，缺失时明确报错（toast 或抛异常由调用方处理），不使用兜底字符串。

## **P2**

### **P2-1 `didChangeDependencies` 覆盖 `videoHeight`**

- **位置**：`view.dart` `didChangeDependencies` 末尾 `..videoHeight = isVertical ? maxVideoHeight : minVideoHeight`
- **问题**：该回调在 MediaQuery、主题、键盘等依赖变化时触发。expanding/collapsing 动画进行中被触发时，会把 `videoHeight` 重置为初始值，导致 `_calcAnimHeight` 计算错误、动画跳变。
- **改法**：加 `!animationController.isAnimating` 守卫；若还需按尺寸变化判断，需先保存旧尺寸并处理首次布局，避免误判。

### **P2-2 `pinnedHeaderSliverHeightBuilder` 里做状态收尾**

- **位置**：`view.dart` `childWhenDisabled` 的 `pinnedHeaderSliverHeightBuilder`
- **问题**：在布局尺寸回调里将 `isExpanding/isCollapsing` 置 false 并排 post-frame 刷新。标志在排回调前已清除，不会重复排队；问题是布局计算与动画状态迁移耦合，收尾逻辑散落在 view，controller 无法单测。
- **改法**：移到 `animationController.addStatusListener` 的 `AnimationStatus.completed` 回调统一处理；注意 `_setVideoHeight` 有 `forward(from: 1)` 分支，`value` 已达 upperBound 会立即 completed，必要时改 `value = 1` + 手动调收尾；监听器在 `onClose` 中移除。
