## 第 1 章 为什么要合并？

主干（`main`）在这段时间里发布了新版本 **2.1.6**，里面有一些和我们相关的更新：

1. 新增 **iOS 画中画（PiP）** 支持；
2. 修了 **Android 上暂停时画面变形** 等问题；
3. 换了一批依赖的**下载地址**（从个人仓库换到官方 fork）；

如果不合并，两条线会越差越远：以后想再合，冲突会更多、更难处理。所以我们在功能相对稳定的时间点做了一次合并。

## 第 2 章 合并时遇到的"冲突"：7 个文件、10 处

机器能自动合并的部分它自己合了；**两处都改过同一行**的地方（共 7 个文件、10 处）需要人来定。

我们用的判断原则是一句话：

> **底层、原理、官方修复 → 听主干的；新功能、新特性、或我们写得更好的写法 → 留我们自己的。**

| 文件 | 它是干什么的 | 为什么冲突 | 最后怎么定 |
| --- | --- | --- | --- |
| `lib/main.dart` | App 的启动流程 | 主干改了"启动失败时怎么退出"，我们把启动拆成了"并排跑、别堵着" | 退出方式用主干的（在 Windows 上有专门写法）；并排启动用我们的 |
| `lib/main.dart` | 同上（另一处） | 主干新增"iOS 画中画初始化" | **两边都要**：既保留我们的"不等待"，也接上主干的画中画初始化 |
| `pubspec.yaml` | 项目清单（版本号、依赖表） | 两边都改了版本号 | 保留我们的 `3.0.1+1`（不降级）；其余依赖项全部用主干的 |
| `lib/pages/setting/models/play_settings.dart` | 设置页的开关列表 | 主干限制"只有 Android 才弹提示"，我们把它改成了更安全的写法 | 合起来：仍然只在 Android 生效，但用我们更安全的写法 |
| `lib/pages/video/controller.dart` | 视频页的控制器 | 主干把方法改名成公开的，我们在里面加了"等转场动画演完再开播" | 名字用主干的（新代码在用它），逻辑保留我们的 |
| `lib/pages/video/view.dart` | 视频页界面 | 主干重构了页面的初始化方式 | 主干的重构保留，我们的"转场延后初始化"保留 |
| `lib/plugin/pl_player/controller.dart` | 播放器控制器 | 两边的 import 和"播放器监听"写法不同 | 合并：主干修的画面问题 + 我们的播放器设置都留着 |
| `lib/services/shutdown_timer_service.dart` | 定时关闭服务 | 两边各加了一个 import | 两个都留 |
| `lib/pages/video/view.dart` | 同上（另一处） | 主干把"初始化哪个介绍页"抽成了函数 | 用主干的函数；我们的转场挂起保留 |

补充一句：主干把播放器的依赖地址换成了官方 fork，我们实测**我们的播放器补丁在两边都能贴上去**，所以地址听主干的，补丁留我们的。

## 第 3 章 怎么证明"没把主干的改动弄丢"？

合并最怕两件事：**把主干的修复弄丢了**，或者**把不该改的地方改回去了**。我们用两个"对答案"的办法检查：

### 办法一：数文件（一眼看全）

- 我们这条线一共改过 **125 个文件**；
- 合并后，与主干**不一样**的文件也正好是 **125 个**；
- 也就是说：**没有出现"我们没碰过、却和主干不一样"的文件** → 不存在"改回去"的情况。

### 办法二：逐行核对（更细）

对**两边都改过**的 32 个文件，我们逐行检查"主干新加的代码，现在还在不在"。

结果：只有 **2 行**"不在"，而且这两行是**我们故意换成更好写法**的：

| 主干原来的写法 | 我们现在用的写法 | 为什么换 |
| --- | --- | --- |
| 直接取变量（`xxx!`，如果为空会直接崩） | 先判断空不空再用（`xxx?.` 加兜底值） | 更安全，不会因为一次初始化失败就崩 |
| 方法的普通版本 | 同名方法，但多了"等转场演完"这层 | 修"转场最后一帧卡一下 / 播放器闪一下" |

结论：**主干的改动一条没丢，我们的改动也都还在。**

## 第 4 章 升级 Flutter：3.47.5 → 3.47.7

### 为什么非升不可？

合并进来的主干要求 Flutter **3.47.7**，而我们电脑里装的是 **3.47.5**。差一个小版本，装依赖时就直接报错：

> 本项目需要 Flutter 3.47.7，当前是 3.47.5 → 依赖解析失败

（Flutter 可以理解成"做 App 的工具箱"，里面既有命令行工具，也有写界面的框架代码。）

### 为什么不能"一键升级"？

我们电脑里的工具箱是**从网上下载的一整份代码（git 检出）**，并且**停在 3.47.5 这个版本标签上**（不是"稳定通道"）。这种情况下官方的一键升级命令用不了，需要**按版本号切换**。

### 实际做的三步

1. **备份 + 切换版本**：先把工具箱里我们贴过的补丁改动导出一份备份，再切换到 3.47.7；
2. **下载配套零件**：切换后第一次运行会下载对应的 Dart 工具（3.13.4 → 3.13.5）和其他零件；
3. **重新贴补丁**：把我们的补丁按原样重新贴回工具箱。

### 三个坑（这次都踩到了）

| 坑 | 现象 | 解决 |
| --- | --- | --- |
| 官方下载源太慢 | 下载只有 1.35MB/s，下到 209MB 就不动了 | 换成国内镜像，速度 **13.4MB/s**（快约 10 倍），几十秒下完 |
| 升级会**冲掉补丁** | 切换版本时，工具箱里我们贴的补丁被"重置"没了 | 升级后**必须重跑一次补丁脚本**（这次重贴了 25 个框架补丁 + 9 个界面库补丁 + 播放器补丁） |
| 补丁脚本"猜目录" | 播放器补丁要贴到"项目实际使用的那份播放器"上，脚本原来是"取最后一个文件夹"，有两个同名候选时会贴错 | 改成**按项目实际使用的版本精确找**，不会再贴错 |

**小知识：我们的补丁贴在两个地方**——① Flutter 工具箱本身（比如顶栏手势、文本选择这些小修改）；② 依赖库里（比如界面的 `material_ui`、播放器的 `media_kit_video`）。所以**以后只要重装了工具箱或重装了依赖，就重跑一次补丁脚本**，让贴纸回来。

## 第 8 章 新增一个"最省电"的视频输出后端

### 先说背景

播放器把一帧画面送上屏幕，通常要经过：**解码 → GPU 渲染 → 贴到界面的纹理上**。
之前可选的后端（`vo=gpu` / `vo=gpu-next`）都走这条路，好处是能加滤镜、超分、截图也方便。

另有一条"抄近路"：**解码器直接把画面画到屏幕上**（`vo=mediacodec_embed`），中间不过 GPU，理论上更省电、延迟更低。

### 接入它的两个硬性条件（mpv 官方文档写的）

| 条件 | 为什么 | 我们的做法 |
| --- | --- | --- |
| 必须 `hwdec=mediacodec` | 该后端只接受 MediaCodec 解码出来的帧 | 选了它以后**强制**走 mediacodec 硬解（覆盖硬解设置里的档位） |
| 必须先告诉 mpv "Surface 在哪"（`wid`） | mpv 里对它有断言，`wid` 为 0 会直接失败或黑屏 | 播放器库本来就是"先设 wid、再设 vo"，顺序天然正确 |

还有一条：该模式**没有** mpv 侧的滤镜 / 着色器链，所以 **Anime4K 超分、截图** 这类功能用不了；
"硬解失败自动降级"在该模式下也没意义（降级到复制模式 / 软解只会黑屏），所以这个模式下不再自动降级，
而是直接提示"这个视频没法用 mediacodec 硬解，请把后端改回默认"。

### 播放器补丁也跟着改了

以前我们的补丁只对 `gpu` / `gpu-next` 做"纹理尺寸同步"，现在把 `mediacodec_embed` 也算进去；
并且把补丁里写死的 `vo=gpu` 改成"用配置里选的那个 vo"（否则选什么都变回 gpu）。

### 怎么验证有没有生效

播放 → 全屏 → 打开「播放信息」面板，看两行：

- `VO`：配置进去的值；
- `CurrentVO`：**实际**在用的后端（看这个才算数）。

## 第 9 章 悬浮底栏的"气泡放大"不再被切边

### 问题

悬浮底栏是一块"玻璃"，玻璃按自己的外形做裁剪。选中气泡原本画在玻璃**里面**，
所以按住放大 1.3 倍时，超出的部分被玻璃边缘切掉，看着像被削平了一块。

### 改法

把底栏拆成**三层同级**（外层容器不裁剪）：

1. 玻璃本体（仍然按外形裁剪，模糊和半透明填色都正常）；
2. 选中气泡（画在玻璃**外面**，所以放大后可以连边框一起超出胶囊）；
3. 图标 / 文字（画在最上面）。

气泡的位置和以前**逐像素一致**，只是绘制层从"玻璃里"挪到了"玻璃外"。
顺带把"按下 / 拖动"的监听器提到最外层，保证手指点在图标上也能收到按下事件。

## 第 10 章 底栏按压震动：一次"试错后回退"的记录

这件事绕了三圈，记下来免得以后再走一遍。

| 阶段 | 做法 | 结果 |
| --- | --- | --- |
| 第一版 | 手指**按下**就震动（选中时本来也会震，所以给"选中回调"加了开关，底栏传 false，避免一次点击震两下） | 结构保留，一直用到现在 |
| 第二版 | 发现系统触感太轻（Flutter 的 `lightImpact` 在 Android 上就是最轻的 `CLOCK_TICK`），改成**自己调原生振动器**：时长 / 振幅可控，还加了「震动强度」三档设置 + `VIBRATE` 权限 + JNI 通道 | 能用，但手感反复调不满意 |
| 第三版 | 按你的要求**改回系统触感**，并把原生振动那一整套（Java 方法、JNI 绑定、权限、设置项、读值）**全部删掉** | 系统触感，但用的 `lightImpact` |
| 第三版修正（2026-10-26） | 实测 `lightImpact` 映射到 `VIRTUAL_KEY`、`mediumImpact` 只是 `KEYBOARD_TAP`，两档都很轻；改用 `heavyImpact`（`CONTEXT_CLICK`，系统长按/上下文菜单那档） | 现在：`feedBack()` = `HapticFeedback.heavyImpact()` |

### 为什么最后选择"删干净"而不是"留着备用"

留着的代价是：多一个"看起来能调、其实没用"的设置项（用户会困惑）、多一条 `VIBRATE` 权限、
多一份 JNI 绑定要维护。功能不用了，就该整条链路一起删。

### 结论（给以后调手感的自己）

- 振动的"时长"压到个位数毫秒（1~5ms）已经**低于马达的物理响应**，很多机型会直接抹平 → 感觉像没震；
- 想"干脆一点"应该**缩短时长 + 降振幅**，而不是把时长压到 1ms；
- 现在的手感完全由系统「设置 → 声音与振动 → 触感反馈」决定，应用侧只有一个总开关
  （**其它设置 → 震动反馈**，默认关）；
- **“系统触感”内部也分强弱**（按 Android 引擎实际映射）：`lightImpact` → `VIRTUAL_KEY`、
  `mediumImpact` → `KEYBOARD_TAP`（这两档都很轻）、`heavyImpact` → `CONTEXT_CLICK`（明显更实）、
  `selectionClick` → `CLOCK_TICK`（最轻）、`vibrate` → `LONG_PRESS`（更长）。嫌弱先用 `heavyImpact`，
  还嫌弱再考虑 `vibrate`，别一上来就重写原生振动。
