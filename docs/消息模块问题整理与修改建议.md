# 消息模块问题整理与修改建议

日期：2026-11-12  
范围：私信获取、未读角标、会话列表刷新、消息详情、发送与撤回、时间标签、消息中心分类及 Android 桌面角标。  
方式：静态代码检查与代码修改；第 1–11、14 条已按本文建议落到代码（见「六、实施状态」），第 12、13 条仍待抓包/实测，示例代码仅作说明。

## 结论摘要

初次静态检查确认了六类与用户反馈直接对应的问题：消息轮询不持续、进入消息列表会清除底部未读角标、返回会话列表后摘要可能过期、每条消息都显示时间、免打扰状态可能回退，以及未读数没有同步到 Android 桌面角标。发送锁未复位、撤回消息仍显示原文、消息 JSON 解析缺少兜底、点赞列表翻页状态未复位等问题也已按第六节实施。当前代码状态及尚待验证事项以「六、实施状态」和「依据与限制」为准。

私信 HTTP/gRPC 接口属于非公开或缺乏完整公开文档的接口。`update_ack` 的 HTTP 方法、消息中心分类接口是否自动推进已读游标等行为，需以官方客户端网络请求或真实账号响应确认；本文不建议凭猜测增加接口。

## 一、用户反馈的六项问题

### 1. 前台运行时消息获取不及时

**位置：** [lib/pages/main/controller.dart#L295](../lib/pages/main/controller.dart#L295)、[lib/pages/whisper/controller.dart#L34](../lib/pages/whisper/controller.dart#L34)、[lib/pages/main/view.dart#L112](../lib/pages/main/view.dart#L112)

消息会话列表在控制器初始化时获取；主控制器有 5 分钟的检查间隔，但它是事件触发检查的节流阈值，不是定时任务。未读检查主要发生在回到前台、路由返回或切换页面等事件，且不会持续刷新会话列表。因此消息页保持打开时，新消息可能长时间不可见。

**建议方案：**

- 回到前台、进入消息页时立即刷新未读数；消息页可见时再刷新会话列表。
- 为前台状态增加可取消的周期检查。建议从 30～60 秒开始，根据请求成本调整；后台时暂停，回前台后立即补查。
- 当前打开的私信会话使用增量同步或官方支持的推送/长连接；不要以刷新整个会话列表代替聊天消息实时同步。
- 加入单请求互斥、错误退避和定时器释放，避免网络慢时请求堆积。

示意代码（省略生命周期状态保存和错误退避的具体接线）：

```dart
Timer? _messageRefreshTimer;
bool _isMessageRefreshRunning = false;

void startMessageRefresh() {
  _messageRefreshTimer?.cancel();
  _messageRefreshTimer = Timer.periodic(
    const Duration(seconds: 45),
    (_) async {
      if (!isAppResumed || _isMessageRefreshRunning) return;
      _isMessageRefreshRunning = true;
      try {
        await queryUnreadMsg();
        if (isMessagePageVisible) {
          await Get.find<WhisperController>().onRefresh();
        }
      } finally {
        _isMessageRefreshRunning = false;
      }
    },
  );
}

void stopMessageRefresh() {
  _messageRefreshTimer?.cancel();
  _messageRefreshTimer = null;
}
```

这里的 `isAppResumed`、`isMessagePageVisible` 应由现有 `WidgetsBindingObserver` 和导航状态提供；不要在后台仍轮询。

### 2. 点击底部“消息”就清除了未读气泡

**位置：** [lib/pages/main/controller.dart#L315](../lib/pages/main/controller.dart#L315)、[lib/pages/main/controller.dart#L353](../lib/pages/main/controller.dart#L353)、[lib/pages/whisper/view.dart#L250](../lib/pages/whisper/view.dart#L250)

`openMsgPage()` 和切换到消息 Tab 的分支会调用 `clearUnreadMsg()`；回复、@、赞、系统通知入口也在跳转前把对应分类数值设为 0。这是纯本地清除，尚未证明该分类在服务端已读。

**建议方案：**

- 打开消息列表只导航和刷新，不清空底部总角标，也不清空分类角标。
- 打开具体未读会话/通知详情并且服务端已读操作成功后，再刷新服务端未读汇总。
- 会话列表行的本地未读状态也应在详情成功加载并 ack 成功后清除；ack 失败时保留或恢复。
- 对回复/@/赞分类先确认官方客户端的已读行为；若对应列表请求会自动更新游标，则以服务端返回的未读数为准；若不会，则抓包确认接口和参数后再接入。

示意：

```dart
void openMsgPage() {
  // 不在这里调用 clearUnreadMsg。
  lastCheckUnreadAt = DateTime.now().millisecondsSinceEpoch;
  final index = navigationBars.indexOf(NavigationBarType.msg);
  if (index != -1) {
    setIndex(index);
  } else {
    Get.toNamed('/whisper');
  }
}

Future<void> onMessageReadSucceeded() async {
  await queryUnreadMsg();
}
```

同样需要从 `setIndex()` 的消息分支移除本地清零；清除时机应由已读请求成功后的状态更新决定，而不是由导航动作决定。

### 3. 从私信详情返回，会话列表仍显示旧内容

**位置：** [lib/pages/whisper/widgets/item.dart#L198](../lib/pages/whisper/widgets/item.dart#L198)、[lib/pages/whisper_detail/controller.dart#L138](../lib/pages/whisper_detail/controller.dart#L138)、[lib/pages/whisper/controller.dart#L109](../lib/pages/whisper/controller.dart#L109)

发送成功时调用的是详情页自己的 `onRefresh()`，它只重新获取当前会话消息。消息列表页面是 keep-alive 页面；详情页返回时没有明确调用 `WhisperController.onRefresh()`，因此最后一条消息、时间和会话排序仍可能是旧数据。

**建议方案：**

- 在打开详情的导航 Future 完成后刷新会话列表；这样除了发送消息，也能覆盖详情停留期间收到的新消息。
- 或由消息页的路由返回回调统一刷新，但只在消息页当前可见时触发。
- 如果后续改为本地更新会话预览，需要同时维护最新消息、时间、未读数和排序；只改预览文字不够。

示意：

```dart
onTap: () async {
  await Get.toNamed(
    '/whisperDetail',
    arguments: detailArguments,
  );

  if (Get.isRegistered<WhisperController>()) {
    await Get.find<WhisperController>().onRefresh();
  }
}
```

实际实现可把 `detailArguments` 替换为当前代码中的参数映射。若列表控制器可能已销毁，应保留注册检查；若返回时消息 Tab 不可见，则可将刷新标记为 dirty，等再次可见时刷新。

### 4. 3 分钟以内的相邻消息不显示时间

**位置：** [lib/pages/whisper_detail/widget/chat_item.dart#L149](../lib/pages/whisper_detail/widget/chat_item.dart#L149)、[lib/pages/whisper_detail/view.dart#L159](../lib/pages/whisper_detail/view.dart#L159)、[lib/common/widgets/flutter/chat_list_view.dart](../lib/common/widgets/flutter/chat_list_view.dart)

每个 `ChatItem` 都会创建时间标签，没有检查相邻消息的时间差。消息列表使用 `reverse: true`，接口消息按时间倒序；建议由列表层基于合并后的消息数据计算显示条件，再传给气泡。

**建议规则：**首条消息显示时间；其余消息仅当与相邻消息间隔大于 180 秒时显示。相邻时间戳差小于或等于 180 秒时隐藏时间和对应留白。分页后也要基于合并后的列表重算，避免分页边界重复显示。

示意代码（数组按时间倒序，`index - 1` 是更新的相邻消息）：

```dart
final currentTime = response[index].timestamp.toInt();
final newerTime = index > 0
    ? response[index - 1].timestamp.toInt()
    : null;
final showTime = newerTime == null ||
    (newerTime - currentTime).abs() > 180;

return ChatItem(
  item: response[index],
  showTime: showTime,
  // 其他参数保持现有传递方式
);
```

`ChatItem` 增加 `showTime` 参数；条件为 false 时不要只隐藏文字，还要移除时间标签的 Padding。若产品希望跨日一定显示日期分隔，应将跨日作为明确的例外规则。

### 5. 关闭免打扰后刷新会回退到原状态

**位置：** [lib/pages/whisper/widgets/item.dart#L116](../lib/pages/whisper/widgets/item.dart#L116)、[lib/pages/whisper/widgets/item.dart#L169](../lib/pages/whisper/widgets/item.dart#L169)、[lib/pages/common/common_whisper_controller.dart#L50](../lib/pages/common/common_whisper_controller.dart#L50)、[lib/http/msg.dart#L463](../lib/http/msg.dart#L463)、[lib/http/msg.dart#L559](../lib/http/msg.dart#L559)、[lib/pages/whisper/controller.dart#L101](../lib/pages/whisper/controller.dart#L101)、[lib/grpc/bilibili/app/im/v1.pb.dart#L4150](../lib/grpc/bilibili/app/im/v1.pb.dart#L4150)

长按会话菜单调用 `MsgHttp.setMsgDnd`，当前按 `isMuted ? 0 : 1` 发送 `setting`。请求成功后只在客户端执行 `item.isMuted = !isMuted`。刷新时，会话列表由 gRPC `SessionMain` 重新返回，`Session.isMuted` 会覆盖本地值。现象说明写入状态与刷新读回状态不一致；仅凭静态代码还不能断定是 `setting` 的 0/1 语义错误、HTTP 写入未持久化，还是 gRPC 列表读回延迟/数据源不一致。

**实测补充（用户反馈）：** 关闭免打扰后 `get_msg_dnd` 已返回 `setting = 0`，但 `SessionMain` 的 `Session.isMuted` 仍返回 `true`，所以问题落在「列表读回与写入数据源不一致」。因此本次实现不再依赖 `SessionMain` 的免打扰位立即正确，而在 `set_msg_dnd` + `get_msg_dnd` 双重确认后把用户选择记到本地覆盖表；`SessionMain` 读回一致或超过 TTL 时自动移除覆盖，避免永久盖住服务端值。该覆盖只影响展示与菜单文案，不改写服务端。

**建议方案：**

- 先用同一会话做一次区分检查：关闭免打扰后读取 `get_msg_dnd`，再刷新 `SessionMain`。若 HTTP 读回仍为开启，优先核对 `setting` 语义、`uid`/`dnd_uid` 参数及接口响应；若 HTTP 读回已关闭而 gRPC `isMuted` 仍为开启，则问题在列表读回同步或数据源一致性。
- 对照官方客户端请求确认 `setting` 的取值含义，不要仅根据当前客户端的乐观反转推断 `0`/`1`。
- 短期内成功写入后用 `getMsgDnd` 核对；刷新会话列表后以核实过的服务端状态更新 UI。若两个接口读回不一致，应优先统一状态来源或延迟/合并列表更新，而不是不断翻转本地布尔值。
- 请求失败时不改本地状态；读回确认失败时提示状态尚未确认，并避免把旧列表值伪装成已成功设置。

示意代码（`setting` 与服务端状态的映射必须先通过官方请求/响应确认）：

```dart
final targetIsMuted = !isMuted;
final targetSetting = targetIsMuted ? 1 : 0;
final result = await MsgHttp.setMsgDnd(
  uid: Accounts.main.mid,
  setting: targetSetting,
  dndUid: talkerUid,
);
if (!result.isSuccess) {
  result.toast();
  return;
}

item.isMuted = targetIsMuted;
loadingState.refresh();

final verify = await MsgHttp.getMsgDnd(uidsStr: talkerUid);
if (verify case Success(:final response)) {
  final persistedSetting = response?.firstOrNull?.setting;
  if (persistedSetting != targetSetting) {
    await onRefresh();
    SmartDialog.showToast('免打扰状态尚未同步，请稍后重试');
    return;
  }
  // 验证通过后，后续列表刷新仍须保证使用同一份已确认状态。
} else {
  SmartDialog.showToast('设置已提交，但未能确认服务端状态');
}
```

当前 `getMsgDnd` 返回的模型只解析 `setting`，且示例按单个 UID 查询，因此 `firstOrNull` 可用于展示验证思路；合并多 UID 批量读取时，应扩展模型以保留 UID 并按 UID 对应，避免错配。

### 6. 小米澎湃 OS 下应用桌面角标不显示未读

**位置：** [lib/pages/main/controller.dart#L181](../lib/pages/main/controller.dart#L181)、[lib/pages/main/view.dart#L494](../lib/pages/main/view.dart#L494)、[android/app/src/main/AndroidManifest.xml#L287](../android/app/src/main/AndroidManifest.xml#L287)、[android/app/src/main/kotlin/com/example/piliplus/MainActivity.kt#L11](../android/app/src/main/kotlin/com/example/piliplus/MainActivity.kt#L11)、[android/app/src/main/kotlin/com/example/piliplus/DownloadForegroundService.kt#L78](../android/app/src/main/kotlin/com/example/piliplus/DownloadForegroundService.kt#L78)、[android/app/src/main/kotlin/com/example/piliplus/DownloadForegroundService.kt#L116](../android/app/src/main/kotlin/com/example/piliplus/DownloadForegroundService.kt#L116)、[lib/services/audio_handler.dart#L47](../lib/services/audio_handler.dart#L47)、[lib/pages/setting/pages/hyperos_compat.dart#L119](../lib/pages/setting/pages/hyperos_compat.dart#L119)

**用户反馈：**小米澎湃 OS 上存在未读消息时，应用图标不显示未读数量或提醒；期望系统支持角标时能显示，用户查看未读后按规则清除。

**修复前静态检查结论：**当时 `msgUnreadCount` 只用于 App 内导航栏/入口的 `Badge`，没有传给 Android 通知或桌面图标。Manifest 的 `POST_NOTIFICATIONS` 只声明通知运行时权限；`MainActivity` 的 MethodChannel 只处理下载前台服务。已有下载通知渠道用于下载进度且设置了 `setShowBadge(false)`，音频通知也不是消息通知。因此，即使 App 内未读数正确，也没有系统角标更新链路。此问题已按第六节新增独立消息通知渠道和 MethodChannel 桥接。

**建议方案：**

- 新增独立的消息通知渠道，Android 8.0 及以上创建渠道时启用 `setShowBadge(true)`；不要复用下载渠道，也不要改掉下载渠道的 `setShowBadge(false)`。
- 由统一的未读状态管理器接收未读总数，在系统允许通知时更新一条低打扰的消息摘要通知，并调用 `setNumber(unreadCount)`；计数归零或用户已读成功后取消摘要通知。通知文本应避免暴露私信内容，并提供开关让用户选择是否启用桌面角标通知。
- 在启动、回到前台、未读数发生变化、已读请求成功及退出登录时同步通知状态。若要求应用在进程被杀后也能实时显示角标，需要可靠的推送通路；纯 Dart 前台轮询不能保证进程停止期间更新。
- 在澎湃 OS 上分别核实通知运行时权限、应用通知总开关、消息通知渠道的角标设置及桌面启动器的角标总开关。通知权限不等于桌面角标授权。
- Android/厂商启动器可能只显示圆点，不一定显示数字；`setNumber()` 是数量提示，不保证所有启动器均渲染数字。应在目标 HyperOS 版本和系统桌面实测，不建议优先依赖小米私有接口。

示意代码（展示系统通知桥接方式，不是当前项目可直接粘贴的完整实现；需接入权限检查、通知点击路由及项目现有的应用图标资源）：

```kotlin
private const val MESSAGE_CHANNEL_ID = "message_badge"
private const val MESSAGE_NOTIFICATION_ID = 0x2001

fun ensureMessageChannel(context: Context) {
  if (Build.VERSION.SDK_INT < Build.VERSION_CODES.O) return
  val manager = context.getSystemService(NotificationManager::class.java) ?: return
  val channel = NotificationChannel(
    MESSAGE_CHANNEL_ID,
    "消息提醒",
    NotificationManager.IMPORTANCE_LOW,
  ).apply {
    description = "显示未读消息提醒"
    setShowBadge(true)
  }
  manager.createNotificationChannel(channel)
}

fun updateMessageBadge(context: Context, unreadCount: Int) {
  val manager = context.getSystemService(NotificationManager::class.java) ?: return
  if (unreadCount <= 0) {
    manager.cancel(MESSAGE_NOTIFICATION_ID)
    return
  }

  val notification = NotificationCompat.Builder(context, MESSAGE_CHANNEL_ID)
    .setSmallIcon(R.drawable.ic_notification_icon)
    .setContentTitle("有未读消息")
    .setContentText("打开应用查看")
    .setNumber(unreadCount)
    .setOnlyAlertOnce(true)
    .setAutoCancel(false)
    .build()
  manager.notify(MESSAGE_NOTIFICATION_ID, notification)
}
```

该方案会产生一条系统通知；若产品不接受常驻/可见通知，应评估系统和目标启动器是否有可靠、受支持的无通知角标接口。不能假定 Android 通知权限或 App 内 `Badge` 本身就能控制桌面图标。

## 二、其他可确认的消息模块问题

### 7. 发送锁在未登录早退后不会释放

**位置：** [lib/pages/whisper_detail/controller.dart#L113](../lib/pages/whisper_detail/controller.dart#L113)

`_isSending = true` 后，未登录分支直接返回，锁不会复位；网络请求异常时也可能跳过末尾复位。

**建议方案：**登录检查放在加锁之前，并用 `try/finally` 覆盖整个发送流程。

```dart
if (!account.isLogin) {
  SmartDialog.showToast('请先登录');
  return;
}
if (_isSending) return;

_isSending = true;
try {
  final res = await ImGrpc.sendMsg(/* 当前请求参数 */);
  // 保留现有成功/失败处理
} finally {
  SmartDialog.dismiss();
  _isSending = false;
}
```

### 8. 撤回消息仍渲染原内容，系统撤回字段未处理

**位置：** [lib/pages/whisper_detail/controller.dart#L62](../lib/pages/whisper_detail/controller.dart#L62)、[lib/pages/whisper_detail/widget/chat_item.dart#L117](../lib/pages/whisper_detail/widget/chat_item.dart#L117)

列表只过滤 `DRAW_BACK` 类型；气泡在 `msgStatus == 1` 时仍先渲染消息正文，再附加“已撤回”。协议模型还包含 `sysCancel`，当前展示逻辑未使用它。

**建议方案：**对已撤回/系统撤回消息用占位内容替换正文；确认协议状态语义后统一识别 `msgStatus`、`sysCancel` 和撤回类型，避免凭单个枚举值过滤合法消息。

```dart
final isWithdrawn = item.msgStatus == 1 || item.sysCancel;
final Widget child = isWithdrawn
    ? const Text('消息已撤回')
    : buildMessageContentSafely(item);
```

如果产品选择完全隐藏撤回记录，也应同时隐藏正文，并检查列表分页和撤回后的本地状态更新一致性。

### 9. 消息内容 JSON 解码没有兜底

**位置：** [lib/pages/whisper_detail/widget/chat_item.dart#L68](../lib/pages/whisper_detail/widget/chat_item.dart#L68)

`jsonDecode(item.content)` 在 `messageContent()` 的异常处理之外；空内容或格式变化可能使 widget 构建直接抛异常。

**建议方案：**把解码与类型解析放在同一异常边界内；失败时显示安全的文本占位或“暂不支持的消息”，不要让单条异常消息使整页构建失败。

```dart
dynamic content;
try {
  content = jsonDecode(item.content);
} catch (_) {
  content = null;
}

final child = content == null
    ? const Text('暂不支持的消息')
    : messageContent(/* 当前参数 */);
```

### 10. “收到的赞”翻页到末尾后，刷新未重置结束状态

**位置：** [lib/pages/msg_feed_top/like_me/controller.dart#L19](../lib/pages/msg_feed_top/like_me/controller.dart#L19)

# **回调地址校验**

开放平台发送的验证请求示例：

```json
{
  "event": "verify_webhooks",
  "content": {
    "data": 1371848576
  },
  "timestamp": "2021-01-01 12:01:01"
}
```

当你收到开放平台 POST 请求，并且事件（event）为`verify_webhooks`时，你需要解析出data值，并将其作为响应：

```json
{
  "data": 1371848576
}
```

# **回调确认**

在业务请求中，收到开放平台发送的回调消息过后，开发者返回http状态码为2xx的post响应，开放平台即视为该请求已送达。如果规定时间内未收到回复，将触发重试机制。

# **重试机制**

开放平台每次发送POST请求会与开发者回调地址建立5s的连接，超时自动断开。若推送Webhooks消息失败则重试，最多推送3次。在这类情况下，你的服务器应进行去重操作。

# **消息来源验证**

我们使用 **SHA1** 签名来签署所有要推送的消息，并在请求的 `x-bilibili-signature` 标头中添加签名。

如要验证消息来源：

1. 将你收到的消息体和你应用的**应用密钥**(secret+request body)生成 **SHA1** 签名。接收开发平台消息的结构体字段顺序需与上面发送的消息格式字段顺序保持一致，否则签名结果会不一致。
2. 将你的签名与 `x-bilibili-signature` 标头中的签名进行对比。如果签名一致，则表示消息来源真实有效。

# **消息结构**

所有的消息格式统一为如下结构：

```json
{
  "event": "",
  "content": {},
  "timestamp": ""
}
```
