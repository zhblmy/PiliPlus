## 2. 渲染层：刷新指示器

### 2.1 转圈独立成重绘层

**问题**

`RefreshLayout.indicator` 收到的是 `AnimatedBuilder(animation: _positionController, …)`，下拉/刷新期间每个 tick 都会重建 `RefreshProgressIndicator`，其内部 `CustomPaint` 于是 `markNeedsPaint()`。SDK 的进度指示器与 `Scrollable` 内部都没有 `RepaintBoundary`，重绘请求一路向上，停在最近的重绘边界——首页那层是 `ClipBelowTopBar` 里的 `RepaintBoundary(child: body)`，**包住了整个 `TabBarView`**。

结果：下拉/刷新期间每一帧都在重跑 `RenderRefreshLayout → body → Scrollable → Viewport → 各 sliver` 的绘制流程，并对 `cacheExtent` 内约 28 个子层各做一次合成；而这期间滚动偏移恒为 0、列表一个像素都没变。（卡片本身因 `SliverChildBuilderDelegate.addRepaintBoundaries` 默认 `true` 不会重录内容。）

**位置**：`lib/common/widgets/flutter/refresh_indicator.dart:527`

**改动**

```dart
indicator: _status == null
    ? null
    // 转圈自成一层的重绘边界：下拉/刷新期间它每帧都在重绘，
    // 不加边界会把整条 scroll view 的绘制流程一起白跑一遍
    : RepaintBoundary(child: AnimatedBuilder(…)),
```

**收益**：重绘范围收敛到 49×49 那块，估 **0.1–0.5 ms/帧**。indicator 只在 drag/refresh 期间存在，边界开销是临时的；`OffsetLayer` 不裁剪，elevation 阴影不受影响。

### 2.2 布局正确性与生命周期

**问题**

1. `heightFactor` / `scaleFactor` 的 setter 直接调 `_layoutIndicator()` → `indicator.layout(...)`：这是在**布局期之外**对子节点做布局，且同一函数里读 `constraints.maxWidth`——`RenderBox.constraints` 在首次布局完成前会抛 `RenderBox was not laid out`，目前不出错**只因为**"`indicator != null` ⇒ 必然已布局过"这条时序巧合。两个 listener 同帧触发时还会布局两次。
2. `_heightFactor` / `_scaleFactor` 从 `0` 起，构造时不读动画当前值：渲染对象在"刷新进行中"重建（页面重建 / keep-alive 复活 / 热重载）时，首帧转圈会画在顶栏后面。
3. listener 只在 `dispose()` 移除：子树 deactivate 但未 dispose 期间，动画仍会往已脱离管线的对象写字段并 `markNeedsPaint()`。
4. `updateRenderObject` 里的"转圈不可见就跳过重排"守卫防的是不存在的场景——`TopBarInset.value` 在滚动期恒定（滚动只改 `collapse` 这个 listenable）。

**位置**：`lib/common/widgets/refresh_layout.dart`（`attach`:114 / `detach`:125 / `sizedByParent`:142 / `performResize`:145 / `computeDryLayout`:157 / `performLayout`:160 / `paint`:186 / `hitTestChildren`:214 / `debugFillProperties`:228）

**改动**

- 删除 `_layoutIndicator()`，指示器的尺寸与偏移统一在 `performLayout()` 内计算；两个 setter 只 `markNeedsLayout()`（相等即 no-op）。
- 构造时用 `position.value` / `scale.value` 初始化因子。
- listener 改由 `attach()` / `detach()` 成对管理，`attach` 时同步一次当前动画值。
- 声明 `sizedByParent => true` + `performResize()`，尺寸只由约束决定（见 §2.3）。
- `updateRenderObject` 只保留判等 + `markNeedsLayout()`。
- 补 `hasBoundedWidth/Height` 断言、`> 0` 判据、`hitTestChildren` 注释（说明为何不混入 `SlottedLayoutMixin`）、`debugFillProperties`。
- `paint` 里 body 的偏移统一为 `getOffset(body) + offset`，与 `hitTestChildren` 一致。

**收益**：消除"布局期外布局子节点 / 读取未就绪 constraints"两个隐患；每帧不再出现"重排 + 立刻手动绘制"的双重驱动，行为与 Flutter 上游 `RefreshIndicator`（`SizeTransition` + `Align`）一致；渲染对象重建后首帧位置正确。

### 2.3 relayout 边界显式声明

**问题**

改成 `markNeedsLayout()` 后，每帧重排是否只影响本节点取决于：

```dart
_isRelayoutBoundary = !parentUsesSize || sizedByParent || constraints.isTight || parent == null;  // SDK object.dart:2863
```

`RefreshIndicator` 外面只要隔一层 proxy（`Padding` / `DecoratedBox` 等）就是 `parentUsesSize: true`，此时只剩"约束恰好 tight"这一条命；遇到宽松约束（非 stretch 的 `Column` 等），下拉期间的重排会逐帧往父链冒泡。

**位置**：`lib/common/widgets/refresh_layout.dart:142-157`

**改动**

```dart
@override
bool get sizedByParent => true;

@override
void performResize() {
  final constraints = this.constraints;
  assert(constraints.hasBoundedWidth && constraints.hasBoundedHeight, …);
  // 尺寸只由约束决定、与子节点无关，所以声明 sizedByParent：
  // 这样本节点永远是 relayout boundary，下拉期间的重排不会往上冒泡
  size = constraints.biggest;
}

@override
Size computeDryLayout(BoxConstraints constraints) => constraints.biggest;
```

**收益**：布局期每帧只重排本节点 + 指示器子树，与父链约束松紧无关；顺带补齐 dry layout 支持。

## 3. 交互：下拉刷新时内容不动

**问题**

`rcmd/view.dart` 给 `CustomScrollView` 显式传了 `BouncingScrollPhysics`，这一层会：

1. `applyPhysicsToUserOffset` 在未越界时**直接返回原始 offset、不调父链**，包内 `RefreshScrollPhysicsMixin`（把拖拽量转成 `onDrag` 并 `return 0.0`）根本不会执行；
2. `applyBoundaryConditions` 返回 `0.0`（允许越界），滚动位置真的变成负值。

结果：下拉时整屏内容跟着手指走、带阻尼回弹，转圈只是"额外出现"——不是 Material 原生的"内容不动、只有指示器出现"。

**位置**

| 作用 | 位置 |
| --- | --- |
| 新增 physics | `lib/common/widgets/scroll_physics.dart:103`（`BouncingScrollPhysicsTopClamped`，边界条件在 `:118`） |
| 使用点 | `lib/pages/rcmd/view.dart:66` |

**改动**

```dart
/// 只在**顶部**夹紧的 [BouncingScrollPhysics]。
class BouncingScrollPhysicsTopClamped extends BouncingScrollPhysics {
  @override
  double applyBoundaryConditions(ScrollMetrics position, double value) {
    if (value < position.pixels && position.pixels <= position.minScrollExtent) {
      return value - position.pixels;          // 顶部下拉：吃掉整段位移
    }
    if (value < position.minScrollExtent &&
        position.minScrollExtent < position.pixels) {
      return value - position.minScrollExtent;  // 回弹不许冲过顶部
    }
    return 0.0;                                 // 其余方向（含底部）保留回弹
  }
}
```

```dart
// rcmd/view.dart
physics: const BouncingScrollPhysicsTopClamped(
  parent: AlwaysScrollableScrollPhysics(),
),
```

**为什么这样能"只出转圈"**：顶部越界被夹紧后滚动位置不变，`ScrollPosition.setPixels` 会 `didOverscrollBy` 派发 `OverscrollNotification`；`RefreshIndicator` 正是靠它累加 `_dragOffset`（`refresh_indicator.dart:346-351`）驱动转圈。起点由 `ScrollStartNotification.dragDetails` 触发（`DragScrollActivity` 保证非空），所以下拉一开始就进入 `drag` 状态。

**收益**

- 下拉时顶部内容**一个像素都不动**，只有转圈滑出并放大、1:1 跟手；
- 底部回弹、惯性手感完全不变（没有用"两端都夹紧"的 `BouncingScrollPhysicsExt`，避免顺手砍掉底部回弹）；
- `RefreshLayout` 无需改动（位置公式复用 `OverscrollNotification` 的累积量）。

## 4. 首屏缓存

### 4.1 缓存模块

**问题**：首屏必须等接口返回（150–400 ms，弱网更久），中间有一次骨架屏 → 卡片的视觉跳变；断网启动直接停在错误页。

**位置**

| 作用 | 位置 |
| --- | --- |
| 解析 / 过滤（app / web 两条路径） | `lib/http/video.dart:82`（`parseWebRcmdItems`）、`:189`（`parseAppRcmdItems`） |
| 上报原始 item | `lib/http/video.dart:55`、`:126`（`onRawItems` 参数） |
| 缓存读写 | `lib/pages/rcmd/rcmd_cache.dart:27`（write）、`:74`（read）、`:19`（按来源拆键） |
| 缓存键 | `lib/utils/storage_key.dart:268`（`rcmdCache`，实际键为 `rcmdCache_app` / `rcmdCache_web`） |

**改动**

1. 把两处"解析 + 过滤"循环抽成 public static 的 `parseWebRcmdItems` / `parseAppRcmdItems`（纯函数；`RcmdCache` 回放时复用同一套过滤，用户新拉黑的 UP、新加的屏蔽词立刻生效），两个 fetch 各加 `onRawItems` 回调上报**过滤前**的原始 item（http 层不碰存储）。
2. 新增 `RcmdCache`：
   - 写：按 `_itemId` 去重 → `take(20)` → 内容指纹 → **`jsonEncode`** 后连同 `ver/src/mid/sig/pages` 存入 `localCache`；
   - 读：校验 `ver/src/mid` → `jsonDecode` → 复用 `parse*Items` 重跑过滤 → 返回 `(items, pages)`；任何异常返回 `null`。
   - 按来源分槽位（`rcmdCache_app` / `rcmdCache_web`），app 与 web 的缓存互不覆盖，来回切模式不用各拉一次。
3. **指纹必须是全量 id，且取不到就不能判等**：`_itemId` 依次取 `id → param → aid → player_args.aid → bvid`。APP 端的 `/x/v2/feed/index` 没有顶层 `id`/`aid`，`bvid` 也不保证存在，**只有 `param` 必然存在**（模型里是不可空的 `int.parse(json['param'])`）。旧实现只认 `id/bvid/aid`，对 APP item 恒为 `null` → 指纹恒等于 `20|null|null` → 第一次写入之后**每次刷新都判定"没变化"而跳过写盘**，缓存永远停在第一次那批内容上（这正是"冷启动一直显示同一批内容、下拉刷新也救不回来"的原因）。现在指纹拼全部条目的 id；只要有一条取不到 id 就返回 `null`，调用方放弃判等、照常写入。
4. 早退判等除 `sig` 外还要校验 `ver` / `src` / `mid` / `pages`：切 app/web 模式或换账号后，旧实现的同一个 `sig` 会让新内容写不进去。
5. `read` 对 `pages` 做 `1..9` 合法性校验，脏数据不会把续页游标推到很远的地方。
6. 存 JSON 字符串而不是嵌套 Map：`hive_ce` 的 `readMap()` 返回 `Map<dynamic, dynamic>`，直接喂给 `Model.fromJson(Map<String, dynamic>)` 会在运行时抛类型错误，被外层 `try/catch` 吞掉 → 缓存静默失效。
7. `_ver` 升到 2：上面那个"冻结缓存"是旧版本写下的，升版让老数据读不出来，用户升级后自动重新建立缓存。

**收益**

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 冷启动到"看到卡片" | 首帧 + 150~400 ms | 首帧（+ 约 3~8 ms 解析 10~20 条） |
| 骨架屏 → 内容跳变 | 有 | 无（有缓存时） |
| 断网启动 | 错误页 | 有缓存即可浏览 + toast 提示"显示的是上次内容" |
| 启动请求次数 | 1 次 | **0 次**（见 §4.2） |

代价：`localCache` 与设置项同 box，`GStorage` 清空时会一起清；不设 TTL。

### 4.2 首屏只读缓存、不自动刷新

**问题**：`onInit` 注入缓存之后仍然无条件 `queryData()`——用户看到缓存，150~400 ms 后顶部内容被替换，本质还是"先给你看，再偷偷换掉"。

**位置**：`lib/pages/rcmd/controller.dart:45`（`onInit`）

**改动**

```dart
if (cached != null) {
  loadingState.value = Success(cached.items);
  _fromCache = true;
  // 缓存里已经包含 `pages` 页内容：续页从下一页开始，
  // 否则会重复请求第二页（APP 端每页 10 条）。
  // 启动期也不再自动发请求，数据新鲜度交给用户下拉。
  page = cached.pages;
  return;
}
// 没有缓存（首次安装 / 缓存损坏 / 换账号）才在启动时请求
queryData();
```

配套三点：

1. `page = cached.pages`（而不是写死 1）：缓存里是 `freshIdx=0` + `freshIdx=1` 两页合并的 20 条，游标停在 1 会让「加载更多」再拉一遍第二页 → 重复卡片。用缓存自带的 `pages` 还能正确处理"刷新时第二页失败、只缓存了一页"的情况（此时 `pages = 1`，不会跳过第 1 页）；
2. 无缓存时仍然 `queryData()`：否则首次安装会永久停在骨架屏且没有重试入口；
3. `onLoadMore` 保留 `if (page == 0 && !isLoading) page = 1;` 作为兜底（刷新失败后 `page` 会被 `onRefresh` 还原成 1，两者不冲突）。

**收益**：冷启动网络请求 **1 → 0 次**；无"缓存被静默替换"的闪烁；**冷启动看到的是上次退出前最后一次刷新写下的内容**（缓存每次刷新都会更新，见 §4.1）。

首次刷新失败时保留缓存内容，并且只用 `_cacheToastShown` 提示一次"显示的是上次内容"。`_fromCache` 在失败时**不清空**（只在刷新成功或加载更多成功时清），这样网络恢复后的第一次成功刷新仍然是**替换**而不是合并——否则会把本次会话用户刚看过的内容当成"上次看到这里"合进来，并插入语义错误的分隔卡。

### 4.3 首次刷新替换而不是合并

**问题**

第一次下拉刷新时 `handleListResponse` 会把缓存合并到新数据后面，并因 `savedRcmdTip` 默认 `true` 插入"上次看到这里"分隔卡——而本次会话用户根本没看过那个位置，卡片语义错误；同时新旧两页都来自 `fresh_idx=0`，**重叠概率很高**，会出现同一张卡重复。

**位置**：`lib/pages/rcmd/controller.dart:199`（`handleListResponse`）

**改动**

```dart
void handleListResponse(List dataList) {
  if (page != 0) return;                  // 只有刷新才需要处理
  final fromCache = _fromCache;
  _fromCache = false;
  _cacheToastShown = false;
  page = _refreshPageSpan - 1;            // 见 §4.4
  // 缓存只是"先给点东西看"：首次刷新直接替换，不与缓存合并
  if (fromCache || !enableSaveLastData) return;

  if (loadingState.value case Success(:final response)) {
    if (response == null || response.isEmpty) return;
    final base = _mergeUnique(dataList, const []);   // 新数据自己去重
    final merged = _mergeUnique(base, [
      if (response.length > 200) ...response.take(50) else ...response,
    ]);
    lastRefreshAt =
        savedRcmdTip && merged.length > base.length ? base.length : null;
    dataList
      ..clear()
      ..addAll(merged);
  }
}
```

**收益**：首次刷新结果是干净的 20 条，无重复卡片、无错位分隔卡；第二次刷新起才恢复"合并 + 分隔卡"的原有能力。

分隔卡位置的计算也一并修正：先给新数据自己按 `bvid` 去重（`base`），再合并旧内容，`lastRefreshAt = base.length`；旧内容全是重复、一条都没留下时不插卡（`lastRefreshAt = null`）。原写法用 `dataList.length` 作下标，一旦去重让列表变短，`view.dart` 里 `index > lastRefreshAt` 的换算会取到越界下标（`response[length]`）→ `RangeError`。旧内容超过 200 条时只保留 50 条，避免列表无限增长。

### 4.4 一次刷新 20 条

**问题**：APP 接口 `/x/v2/feed/index` **每页固定 10 条**（无页大小参数），而首页 `_cacheExtent = 700` 一屏能显示约 7 行，10 条只够一屏多一点。

**位置**：`lib/pages/rcmd/controller.dart:14`（`_appRefreshPages`）、`:71`（`customGetData`）、`:81`（`_fetchRefresh`）、`:119`（`_fetchAppPage`）、`:137`（`_removeExisting`）、`:153`（`_mergeUnique`）

**改动**

- `customGetData`：`page == 0` 走 `_fetchRefresh()`；否则单页（`_refreshPageSpan = 1`）。
- `_fetchRefresh()`：
  - **app**：`Future.wait` 并行发 `freshIdx=0` 与 `freshIdx=1`（总延迟≈一页），按 `bvid`（退化 `aid`）去重合并成 20 条；两页的**原始** item 合并后一次性写缓存，并按**第二页是否真的解析成功**记录 `pages`（失败时只有 1 页，游标就只前进一页，不会跳过第 1 页的内容）；
  - **web**：本来就是 `ps: 20`，一次请求即可，`pages = 1`。
- `_fetchAppPage()`：把单页异常收敛成 `Error`。并行时若某一页抛异常，`Future.wait` 会整体抛出——不仅丢掉另一页已成功的结果，异常还会穿过 `queryData` 把 `loadingState` 留在 `Loading()`（永远停在骨架屏）。
- `handleListResponse`：`page = _refreshPageSpan - 1`，让 `queryData` 结尾的 `page++` 落在**续页游标**上（app 刷新两页后 `page = 2`，下一次 loadMore 用 `freshIdx=2`），不会重复拉第二页。
- 加载更多走 `_removeExisting`：服务端偶尔返回与已有内容重复的条目，就地剔除（刷新路径的 `_mergeUnique` 管不到 `queryData` 里那句裸 `addAll`）。

**收益**

- 一次刷新 20 条（约 2 屏多），首屏可划内容翻倍；
- 并行两页 → 延迟与单页基本相同，不增加等待；
- 游标正确 → 刷新后再划到底不会重复出现同一批内容（冷启动读缓存时同样正确，见 §4.2）；
- 第二页失败只少 10 条，不影响这次刷新，也不会让游标跳页。

## 5. 启动链路

**问题**

`main.dart` 在 `runApp` 之前执行 `Request(); Request.setCookie(); RequestUtils.syncHistoryStatus();`，其中 `Request.setCookie()` 里除了必需的"账号拦截器 + buvid 激活"，还包含：

| 调用 | 性质 | 与首屏相关 |
| --- | --- | --- |
| `LoginUtils.setWebCookie()` | **每个 cookie 一次 method channel**，首次还会初始化 WebView CookieManager | ❌ |
| `setCoin()` | 网络（余额未缓存时） | ❌ |

再加上 `HomeController.onInit` 里的 `querySearchDefault()`（WBI 签名 + 请求），启动瞬间最多有 **3 个额外网络请求 + N 次 channel** 与首屏推荐流抢同一个 HTTP/2 连接。

**位置**

| 改动 | 位置 |
| --- | --- |
| 拆分 cookie 初始化 | `lib/http/init.dart:44`（`setCookie`）、`:51`（`setCookieDeferred`） |
| 注册 post-frame | `lib/main.dart:186` |
| 默认搜索词先读缓存 | `lib/pages/home/controller.dart:65`（onInit 分支）、`:109`（`querySearchDefault`） |
| 搜索词缓存键 | `lib/utils/storage_key.dart:269` |

**改动**

- `Request.setCookie()` 只保留 `accountManager` + `interceptors.add` + `Accounts.refresh()`；
- 新增 `Request.setCookieDeferred()`（WebView cookie + 硬币余额），与 `syncHistoryStatus()` 一起放进 `addPostFrameCallback`；
- `HomeController`：启动期先从 `localCache` 同步读上次的搜索词，请求改为 post-frame 静默刷新，成功后写回缓存。

**收益**

- 首帧前少 N 次 method channel（cookie 通常十几到几十条）+ 最多 3 个网络请求；
- 搜索框提示词**首帧就正确**（原来为空，等请求回来才出现），且不再有启动请求；
- WebView 相关页面只可能由用户点击进入，post-frame 时 cookie 早已就绪；登录流程本来也会再次调用 `setWebCookie`。

## 9. 风险与回滚

| 行为变化 | 回滚方式 |
| --- | --- |
| 有缓存时启动不再自动刷新 | 删掉 `onInit` 里的 `return`，`queryData()` 会照常执行，其余逻辑不受影响 |
| 首屏请求失败时保留缓存 + toast，而不是错误页 | 把 `handleError` 里的 `if (_fromCache && !_cacheToastShown)` 分支改成 `return false`（一行） |
| 下拉刷新时内容不再位移 | 把 `rcmd/view.dart` 的 physics 换回 `BouncingScrollPhysics` |
| 一次刷新发两个推荐流请求（凑 20 条） | 把 `_appRefreshPages` 改成 `1`，退回单页 10 条 |

- 缓存相关全部包在 `try/catch` 且读取失败返回 `null`，**最坏表现等同于改动前**（回落骨架屏），不存在"启动被缓存卡住"的路径。
- 升级后第一次冷启动会重建缓存：`_ver` 从 1 升到 2、键名也从 `rcmdCache` 变成 `rcmdCache_app` / `rcmdCache_web`，旧数据既读不出来也不会被清理（只是几个 KB 的死键）。**期间老用户会看到一次骨架屏**，这是预期行为。
- 统一回滚：改动集中在 11 个文件，彼此无外部依赖，`git revert` 对应提交即可；`RcmdCache` 是新增文件，删除后 `localCache` 中残留的 `rcmdCache` / `searchDefault` 键不会被任何代码读取。
