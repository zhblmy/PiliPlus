## 2. 采集方法（本次最关键的部分）

### 2.1 为什么不用常见手段

| 手段 | 结论 |
| --- | --- |
| `adb shell input swipe` 驱动 | 小米需「开发者选项 → USB 调试（安全设置）」，本次一直未被系统认可（`settings get global adb_security_enabled` 始终为 null），注入报 `SecurityException: INJECT_EVENTS` |
| `dumpsys gfxinfo <pkg>` | Flutter 自绘、不走 HWUI，帧统计基本为空，**无效** |
| `dumpsys SurfaceFlinger --latency` | 可行（首行 8333333 ns 即 120Hz 周期），但只反映"呈现"，不区分 UI / Raster |
| `integration_test` + `flutter drive` | **不可用**：本项目自建 `ScaledWidgetsFlutterBinding`（`lib/common/widgets/scale_app.dart`，`_binding ??=` 不看 `WidgetsBinding.instance`），与 `IntegrationTestWidgetsFlutterBinding` 冲突 |

### 2.2 最终采用：进程内 autopilot + FrameTiming

新建临时文件 `lib/perf_autopilot.dart`，在 `main()` 末尾按编译期开关启用：

```dart
if (const bool.fromEnvironment('PERF_AUTOPILOT')) {
  PerfAutopilot.start();
}
```

`PerfAutopilot` 做两件事：

1. **合成真实指针事件驱动滚动**（不经过系统注入，无需任何权限）：
   `GestureBinding.instance.handlePointerEvent(PointerDownEvent / PointerMoveEvent / PointerUpEvent)`，
   位置取自 `WidgetsBinding.instance.renderViews.first.size`（逻辑坐标），
   每 12ms 一个 Move 步进，可控制滑动时长与距离。
2. **采集逐帧耗时**：`SchedulerBinding.instance.addTimingsCallback`，
   按场景分桶统计 `FrameTiming.buildDuration`（UI）与 `rasterDuration`（Raster）的
   p50 / p90 / p99 / max，以及超过 8.34ms（120Hz 预算）与 16.67ms 的帧数。

三个场景（启动 9 秒后依次执行，避开骨架屏）：

| 场景 | 动作 |
| --- | --- |
| `home-fling` | 上滑 8 次（每次 200ms、位移 55% 屏高、间隔 150ms） |
| `home-slow-down` | 下滑 3 次（每次 600ms、位移 35%） |
| `home-slow-up` | 上滑 3 次（每次 600ms、位移 35%） |

结果用 `debugPrint` 输出到 logcat（tag `flutter`），以 `PERF_REPORT` 开头。
采集脚本 `build/perf-run.ps1`：安装 → 清 logcat → 冷启动 → 等 34 秒 → `adb logcat -d | Select-String PERF_REPORT`。

### 2.3 踩坑记录

- `Tee-Object`/`Select-Object -Last N` 会吃掉前面的错误输出，**构建失败时看不到原因**；
  改用 `2>&1 | Out-File -FilePath build\xxx.log -Encoding utf8` 再 grep。
- 自定义类名**不能叫 `ScrollActivity`**：`package:flutter/widgets.dart` 已有同名抽象类，
  编译报 `imported from both`。
- `dumpsys SurfaceFlinger --list` 的条目形如
  `RequestedLayerState{521920 SurfaceView[...](BLAST)#29481 parentId=29480}`，
  传给 `--latency` 的必须是**纯图层名**（`SurfaceView[...](BLAST)#29481`），
  要用正则 `SurfaceView\[com\.example\.piliplus/[^\]]*\]\(BLAST\)#\d+` 提取。

## 3. 基线数据（未改动代码）

| 场景 | 帧数 | UI p50 | UI p90 | UI p99 | UI max | **Raster p50** | **Raster p90** | **Raster p99** | **Raster max** | 总耗时 p90 | Raster >8.34ms / >16.67ms |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| home-fling | 163 | 0.61 | 3.91 | 14.15 | 34.94 | 3.70 | 6.32 | 10.88 | 23.15 | 10.60 | 9 / 1 |

**判读**：

- **UI（Dart 构建/布局）非常健康**：p50 只有 0.6ms，p90 1.5~3.9ms，远低于 8.33ms 预算。
  说明列表虚拟化、图片 `memCacheWidth`、`RepaintBoundary` 这些既有优化是有效的。
- **瓶颈在 Raster（GPU）**：p50 就有 3.5~3.8ms（占预算 45%），p99 冲到 10~20ms，单帧最高 26ms。
- 120Hz 下 `总耗时 p90` 为 8.9~10.6ms，**已越过 8.33ms 预算**，对应实际帧率掉到约 90~100fps。

## 4. 归因实验（A/B）

只改一个变量：在 `LiquidGlass` 里让 `lowPower` 恒为 true，即**彻底不建 `BackdropFilter`**
（玻璃栏变成 alpha 0.94 的近不透明纯色底），用 `--dart-define=PERF_NO_BLUR=true` 控制。

| 场景 | 指标 | 基线 | 关模糊 | 变化 |
| --- | --- | --- | --- | --- |
| home-fling | Raster p50 | 3.70 | 3.15 | −15% |
| home-fling | Raster p90 | 6.32 | 4.82 | **−24%** |
| home-fling | Raster p99 | 10.88 | 7.93 | **−27%** |
| home-fling | Raster max | 23.15 | 9.75 | **−58%** |
| home-slow-down | Raster p99 | 19.84 | 6.38 | **−68%** |
| home-slow-down | Raster max | 26.34 | 7.51 | **−71%** |
| home-slow-up | Raster p99 | 16.24 | 6.59 | −59% |
| 合计 | Raster >16.67ms 帧数 | 6 | **0** | 全部消失 |

**结论**：`BackdropFilter`（玻璃顶栏 + 悬浮底栏的高斯模糊）是滚动时 Raster 开销的**主要来源**。
原因是它每帧都要对下层正在移动的画面重新做一次全宽模糊。

## 5. 优化方案与复测

### 5.1 方案

不做"永久关掉模糊"（会丢失玻璃质感），而是**只在滚动期间降级、停下 300ms 后自动恢复**：

- 新增 `lib/utils/scroll_perf.dart`：`ScrollPerf.isScrolling`（`RxBool`）+ `mark()`，
  每次位移重置 300ms 定时器，超时自动置回 false。
- `lib/main.dart`：在 MaterialApp builder 的移动端分支包一层
  `NotificationListener<ScrollNotification>`，只对 `ScrollUpdateNotification` 且
  `metrics.axis == Axis.vertical` 调 `ScrollPerf.mark()`（横向 TabBarView 不算）。
- `lib/common/widgets/liquid_glass.dart`：把 `ScrollPerf.isScrolling.value`
  并入已有的 `lowPower` 判断（该分支原本用于省电/温控降档，复用即可，无需另写一套）。

### 5.2 复测数据

| 场景 | 指标 | 基线 | 优化后 | 变化 |
| --- | --- | --- | --- | --- |
| home-fling | UI p90 | 3.91 | 3.11 | −20% |
| home-fling | Raster p50 | 3.70 | **3.12** | **−16%** |
| home-fling | Raster p90 | 6.32 | **5.37** | **−15%** |
| home-fling | Raster >8.34ms 帧数 | 9 | 6 | −33% |
| home-slow-down | Raster p50 | 3.54 | **3.19** | −10% |
| home-slow-down | Raster p90 | 5.83 | **4.40** | **−25%** |
| home-slow-down | Raster max | 26.34 | 15.81 | −40% |
| home-slow-down | Raster >8.34ms 帧数 | 10 | 5 | −50% |
| home-slow-up | Raster p90 | 5.21 | 4.71 | −10% |

### 5.3 未达预期的地方（如实记录）

- **p99 / max 反而变差**：`home-fling` 的 Raster p99 从 10.88 升到 13.84、max 22.03；
  而"永久关模糊"版本 p99 只有 7.93。推测是**滚动停止 300ms 后恢复 `BackdropFilter`** 的那一两帧
  开销很大（层结构切换 + 首帧模糊）。它发生在画面静止时，主观上不容易察觉，但会污染统计。
- **单次测量波动明显**：`home-slow-up` 的超预算帧数从 3 变成 4，属于噪声，不宜当结论。
- 更彻底的做法是"**保留 `BackdropFilter` 但滚动时把 sigma 置 0**"（不切换层结构），
  本次未验证。

### 5.4 视觉影响

滚动中截屏确认：顶栏/底栏变为 alpha 0.94 的近不透明底，被遮住的卡片内容只剩极淡的透出，
滚动时几乎无感；停下 300ms 后恢复模糊。**未做主观手感评审**。

## 6. 顺带定位到、但本次未修的问题

按预期收益排序，都是用户明确反馈"卡"的场景：

1. **首页分页触发整屏重建** —— `lib/pages/rcmd/view.dart:72` 用 `Obx` 包住整个 `SliverGrid`，
   且 `onLoadMore()` 挂在 `itemBuilder` 里（`:106`）。分页数据到达时会重建全部已构建卡片，
   与滚动同帧发生。基线里 `UI max` 27~35ms 的尖峰大概率来自这里。
2. **视频页每帧重建两处** —— `lib/pages/video/view.dart:548` 的 `SimpleAppBar`
   （每帧算 `Color.lerp`）与 `:764` 的悬浮工具栏（`Obx` 里重建 Stack + 5 个 IconButton），
   都由 `scrollRatio`（`RxDouble`，每帧变）驱动；工具栏外层还有 `Opacity`
   （0 < v < 1 时触发 saveLayer）。
3. **视频页展开/收起动画每帧全屏重排** —— `lib/pages/video/controller.dart:209`
   的 `_animListener` 每帧调 `_calcAnimHeight()` + `refreshPage()`，
   200ms 动画期间每帧重建整个 `ExtendedNestedScrollView`。
