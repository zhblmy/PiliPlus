# PiliPlus 私信未读状态同步问题：原因分析与修复方案

| 项目 | 内容 |
| --- | --- |
| 问题 | 点开私信会话后未读提示消失，再次打开又出现 |
| 影响范围 | 私信列表 `/whisper`、私信详情 `/whisperDetail`、二级会话列表、底栏"消息"角标、长按"标为已读" |
| 代码基线 | `26ee9cf21`（分支 `feature`） |
| 调查时间 | 2026-11-09 |
| 结论 | 客户端确实调用了标记已读接口，但**发送的 `ack_seqno` 取错了值**：详情页发了"本页最旧一条"，长按"标为已读"发了"当前已读指针"。修正两处取值即可，不需要新增任何网络请求 |
| 改动量 | 必改 2 个文件约 12 行；可选优化 2 个文件 |

---

## 1. 结论摘要

| 问题 | 结论 |
| --- | --- |
| 现象是否可复现 | 是，可从代码完整推导，并可稳定复现 |
| 直接原因 | 详情页调 `update_ack` 时，`ack_seqno` 传的是 `msgs.last.msgSeqno`，而消息列表是**时间倒序**，`last` 是本页**最旧**一条 → 服务端只把很早以前那条标为已读，未读数不变 |
| 次要原因 | 长按"标为已读"把 `sessionDetail` 返回的 `ackSeqno`（**当前已读位置**）原样发回 → 空操作，却弹出"已标为已读"的成功提示 |
| 为什么会反复出现 | 列表点击只做了**本地乐观清除**；切回"消息"Tab 或下拉刷新会重新拉服务端会话列表，未读被服务端数据覆盖回来 |
| 修复方式 | ① 详情页改发"会话最新一条"并只在刷新时发；② 长按"标为已读"不再传 `ack_seqno`（服务端默认标到最新）；③ 列表点击保持乐观清除，不加请求 |
| 新增网络请求 | **0**；每次打开会话仍是 1 次 `update_ack`（还会少掉翻页时的多余 ack） |

---

## 2. 问题现象与复现

### 2.1 现象

- 打开"消息"页，列表项显示未读角标。
- 点进某个会话再返回，未读提示消失。
- 切到其他 Tab 再切回"消息"（或下拉刷新、冷启动）后，未读重新出现。
- 长按会话选"标为已读"，同样会在刷新后回弹。

### 2.2 最小复现步骤

1. 账号 B 给账号 A 发送 2 条以上私信（会话中必须有多条历史消息）。
2. 账号 A 在 PiliPlus 打开"消息"页，确认列表项有未读角标。
3. 点开该会话，返回。
4. 切到其他 Tab 再切回"消息"，或下拉刷新列表。
5. 预期无未读，实际未读重新出现。

### 2.3 影响面

| 入口 | 是否受影响 | 说明 |
| --- | --- | --- |
| `/whisper` 私信列表 | 是 | 点击后本地清除，服务端未清 |
| 二级列表（未关注人 / 折叠 / AI / 客服） | 是 | 复用同一个列表项组件 `WhisperSessionItem` |
| 长按 / 右键 → "标为已读" | 是 | 接口调用成功但实际未改变服务端状态 |
| 底栏"消息"角标 | 是（延迟） | 角标来自服务端 `single_unread` 计数，下次查询时回弹 |

| 步骤 | 本地状态 | 服务端状态 |
| --- | --- | --- |

| 2. 点击列表项 | `clearUnread()` → 未读 0（仅内存） | 未读 2 |

## 4. 原因分析

### 4.1 前提一：消息列表是时间倒序的

`msgs.last` 是**本页最旧**的一条，而不是最新。依据：

1. 聊天列表固定倒序渲染：`reverse: true`（`lib/common/widgets/flutter/chat_list_view.dart:44`），`index 0` 在屏幕底部，即最新消息。
2. "加载更多"发生在 `index == response.length - 1`（`lib/pages/whisper_detail/view.dart:166-168`），也就是列表最顶部，即最旧消息。
3. 分页游标 `msgSeqno = msgs.last.msgSeqno` 被当作 `endSeqno` 去取更早的消息（`lib/pages/whisper_detail/controller.dart:49`、`160-165`）；接口约定 `end_seqno` 是"以本序列号结束（不含）"，只有 `last` 是最旧时才成立。
4. 接口约定：`fetch_session_msgs` 返回的 `messages` 按发送时间**逆向**排序。

### 4.2 前提二：`ack_seqno` 表示"把这条及之前标为已读"

- `update_ack` 的 `ack_seqno`：**设置为已读的消息序列号，留空表示最新的消息**；即包含该条及其之前的所有消息。
- `SessionInfo.ack_seqno`：**最近一次已读的消息序列号**，是"已读指针"，只读语义。
- `SessionInfo.max_seqno` / `RspSessionMsg.max_seqno`：会话最新消息的序列号，这才是"标记整段会话已读"应该传的值。

### 4.3 原因一：详情页把"最旧一条"当成 `ack_seqno`

`lib/pages/whisper_detail/controller.dart:55` 传的是 `msgs.last.msgSeqno`：

- 该值通常远早于当前已读指针 → 服务端等于"把很久以前已读的那条再标一遍"，未读计数不变；
- 若服务端不做单调性保护，还可能把已读指针往回拨，导致已读消息重新变未读；
- 请求返回 `code == 0`，客户端不会报错，问题被完全掩盖。

### 4.4 原因二：长按"标为已读"把"已读指针"当 `ack_seqno`

`lib/pages/whisper/widgets/item.dart:40-60`：

```dart
final res = await ImGrpc.sessionDetail(talkerId: talkerUid, sessionType: 1);
if (res case Success(:final response)) {
  final res = await MsgHttp.ackSessionMsg(
    talkerId: talkerUid.toInt(),
    ackSeqno: response.ackSeqno.toInt(),   // 当前已读位置，发回去等于没操作
  );
  if (res.isSuccess) {
    SmartDialog.showToast('已标为已读');    // 成功提示具有误导性
    item.clearUnread();
    ...
```

`sessionDetail().ackSeqno` 是"已经读到哪"，不是"要标到哪"。把它发回去不改变任何状态，但本地清了 UI、还弹了成功提示。

### 4.5 为什么表现为"消失后又出现"

两个独立的"已清"假象叠加：

1. `onTap` 的 `item.clearUnread()` 改的是内存里的 protobuf 对象，行内角标立刻消失；
2. 进入"消息"Tab 时 `clearUnreadMsg()` 会把底栏角标手动置空（`lib/pages/main/controller.dart:373-375`）。

而服务端从未收到有效的已读标记，任何一次重新拉取都会把未读带回来。切换 Tab 时的强制刷新（`_refreshMsgPage`）是最常见的触发点。

### 4.6 附带发现

1. **翻页时会重复 ack**：`customHandleResponse` 对 `isRefresh == false` 同样执行，每向上翻一页就多发一次 `update_ack`（且发的是更旧的序列号）。
2. **请求方法可疑**：`lib/http/msg.dart:360` 用的是 `Request().get(...)`，但 `lib/http/api.dart:519-528` 的注释写的是"标记已读 POST"，同族的 `removeMsg` / `setTop` 也都是 POST + `urlencoded`（`lib/http/msg.dart:246-268`、`319-343`），接口文档标注的也是 POST。"返回 code=0"不能证明已读生效，建议抓包确认并对齐。
3. **命名掩盖了语义**：`msgSeqno` 实际是"分页游标 / 本页最旧"，却容易被当成"最新"，是本次两处取错的共同根源。
4. **陌生人提示消息不 ack 是有意行为**：单条 `msgType == 18 && msgSource == 18` 时不标记已读，修复时必须保留。

## 5. 修复方案

### 5.1 设计原则

1. **"已读"只在一个地方标记**：详情页拿到消息列表时（这才是"真的读了"）。
2. **列表只做乐观 UI**，不加网络请求、不阻塞跳转。
3. **`ack_seqno` 永远传"会话最新一条"**，绝不用本页最旧，也绝不用会话已有的已读指针。
4. **只在首屏 / 刷新时 ack**，翻页不重复发。
5. **命名防回归**：`msgSeqno` 改名为 `oldestSeqno`，并在 `ackSessionMsg` 参数上注明"必须是会话最新一条"。

### 5.2 改动一（必改）：详情页改发最新一条，且只在刷新时发

文件：`lib/pages/whisper_detail/controller.dart`

修改前（46-62 行）：

```dart
@override
bool customHandleResponse(bool isRefresh, Success<RspSessionMsg> response) {
  List<Msg> msgs = response.response.messages;
  if (msgs.isNotEmpty) {
    msgSeqno = msgs.last.msgSeqno;
    if (msgs.length == 1 &&
        msgs.last.msgType == 18 &&
        msgs.last.msgSource == 18) {
      // 特殊提示消息，不标记已读
    } else {
      ackSessionMsg(msgs.last.msgSeqno.toInt());   // ← 最旧一条
    }
    msgs.removeWhere((e) => e.msgType == MsgType.EN_MSG_TYPE_DRAW_BACK.value);
    eInfos ??= <EmotionInfo>[];
    eInfos!.addAll(response.response.eInfos);
  }
  return false;
}
```

修改后：

```dart
@override
bool customHandleResponse(bool isRefresh, Success<RspSessionMsg> response) {
  final msgs = response.response.messages;
  if (msgs.isNotEmpty) {
    // 分页游标：本页最旧一条，仅用于继续向上翻页，不能拿去做 ack
    msgSeqno = msgs.last.msgSeqno;

    final isHint = msgs.length == 1 &&
        msgs.last.msgType == 18 &&
        msgs.last.msgSource == 18;

    // 只在首屏/刷新时标已读；翻页（isRefresh == false）不重复 ack
    if (isRefresh && !isHint) {
      // 消息倒序返回：maxSeqno 是会话最新一条；缺失时退回本次拉到的最新一条
      final newest = response.response.hasMaxSeqno() &&
              response.response.maxSeqno > Int64.ZERO
          ? response.response.maxSeqno
          : msgs.first.msgSeqno;
      ackSessionMsg(newest.toInt());
    }

    msgs.removeWhere((e) => e.msgType == MsgType.EN_MSG_TYPE_DRAW_BACK.value);
    eInfos ??= <EmotionInfo>[];
    eInfos!.addAll(response.response.eInfos);
  }
  return false;
}
```

要点：

- `RspSessionMsg` 有 `maxSeqno` 字段和 `hasMaxSeqno()`（`lib/grpc/bilibili/im/interfaces/v1.pb.dart:3643`）。
- 只做最小改动时，`ackSessionMsg(msgs.first.msgSeqno.toInt())` 同样正确（倒序下 `first` 就是最新）；用 `maxSeqno` 的好处是不依赖列表顺序。
- `msgSeqno` 必须继续赋"最旧一条"，它服务于分页，不能改成最新。
- 保留 `18/18` 不 ack 的既有行为。

### 5.3 改动二（必改）：长按"标为已读"不再传 `ack_seqno`

文件：`lib/pages/whisper/widgets/item.dart`

修改前（40-60 行）：

```dart
Future<void> _updateAck(BuildContext context) async {
  final talkerUid = item.id.privateId.talkerUid;
  final res = await ImGrpc.sessionDetail(talkerId: talkerUid, sessionType: 1);
  if (res case Success(:final response)) {
    final res = await MsgHttp.ackSessionMsg(
      talkerId: talkerUid.toInt(),
      ackSeqno: response.ackSeqno.toInt(),   // ← 已读指针，等于空操作
    );
    if (res.isSuccess) {
      SmartDialog.showToast('已标为已读');
      item.clearUnread();
      if (context.mounted) {
        (context as Element).markNeedsBuild();
      }
    } else {
      res.toast();
    }
  } else {
    res.toast();
  }
}
```

修改后（去掉 `sessionDetail` 往返，服务端默认标到最新）：

```dart
Future<void> _updateAck(BuildContext context) async {
  final talkerUid = item.id.privateId.talkerUid;
  // 不传 ack_seqno：服务端默认把该会话标记到最新一条
  final res = await MsgHttp.ackSessionMsg(talkerId: talkerUid.toInt());
  if (res.isSuccess) {
    SmartDialog.showToast('已标为已读');
    item.clearUnread();
    if (context.mounted) {
      (context as Element).markNeedsBuild();
    }
  } else {
    res.toast();
  }
}
```

若暂时不想改 `MsgHttp.ackSessionMsg` 的签名，等价的最小改法：保留 `sessionDetail`，把 `response.ackSeqno` 换成 `response.maxSeqno`（`lib/grpc/bilibili/im/type.pb.dart:3422`）。

### 5.4 改动三（建议）：`ack_seqno` 可选 + 对齐 POST

文件：`lib/http/msg.dart`（346-370 行）

```dart
static Future<LoadingState<void>> ackSessionMsg({
  required int talkerId,
  int? ackSeqno, // 为空表示标记到会话最新一条
}) async {
  final csrf = Accounts.main.csrf;
  final Map<String, Object> data = {
    'talker_id': talkerId,
    'session_type': 1,
    if (ackSeqno != null) 'ack_seqno': ackSeqno,
    'build': 0,
    'mobi_app': 'web',
    'csrf_token': csrf,
    'csrf': csrf,
  };
  // 签名必须在参数最终确定之后算，否则 w_rid 对不上
  final params = await WbiSign.makSign(data);
  final res = await Request().post(
    Api.ackSessionMsg, // 该常量已含完整域名
    data: params,
    options: Options(contentType: Headers.formUrlEncodedContentType),
  );
  if (res.data['code'] == 0) {
    return const Success(null);
  } else {
    return Error(
      "message: ${res.data['message']},"
      " msg: ${res.data['msg']},"
      " code: ${res.data['code']}",
    );
  }
}
```

说明：

- `ack_seqno` 可选是 §5.3 的前提；`makSign` 必须包含/省略字段之后再调用。
- GET → POST 是**独立变更**，建议单独提交，先抓包确认 GET 是否真的生效；若线上 GET 已被接受，可以只做可选参数。

### 5.5 备选方案（可选，非必需）

只有产品明确要求"即使详情页加载失败也要立刻标已读"时才需要。此时优先用 gRPC 单会话清未读，而不是再发两次 HTTP：

```dart
// onTap 中先跳转，再后台发；不要 await 阻塞跳转
// item.dart 需补 import 'dart:async';
unawaited(ImGrpc.clearUnread(sessionId: item.id));
```

- `ClearUnreadReq` 原生带 `sessionId` 字段（`lib/grpc/bilibili/app/im/v1.pb.dart:726-755`），`ImGrpc.clearUnread` 支持该参数（`lib/grpc/im.dart:93-105`）。
- 仓库中目前只用过 `pageType` 形式，落地前必须实测服务端是否接受单会话清未读；不通过就保持 §5.2 + §5.3 的方案。
- 正常路径下详情页已会把已读标对，不建议为此额外增加请求。

### 5.6 变更清单与影响

| 文件 | 位置 | 改动 | 必选 |
| --- | --- | --- | --- |
| `lib/pages/whisper_detail/controller.dart` | `customHandleResponse`（46-62） | ack 改发 `maxSeqno`/`first`，并加 `isRefresh` 判断 | 是 |
| `lib/pages/whisper/widgets/item.dart` | `_updateAck`（40-60） | 去掉 `sessionDetail`，不传 `ack_seqno` | 是 |
| `lib/http/msg.dart` | `ackSessionMsg`（346-370） | `ackSeqno` 改可选、改 POST | 建议 |
| `lib/pages/whisper*/…` | `msgSeqno` 字段 | 改名 `oldestSeqno` 并补注释 | 建议 |

- **行为变化**：只是把 ack 的序列号从"最旧"改为"最新"，并去掉翻页时的重复 ack；接口契约不变。
- **请求量**：打开会话仍为 1 次 `update_ack`；长按"标为已读"从 2 次降为 1 次；列表点击仍为 0 次。
- **不影响**：置顶、免打扰、删除会话、折叠/系统会话、陌生人提示消息的既有逻辑。
- **回滚**：两处必改互相独立，可单独回滚，无数据迁移。
- **已知残留**：ack 是异步的，若"点开→秒退→立刻切回消息 Tab"，刷新可能早于 ack 返回，出现一次瞬时回弹，下次刷新自愈；不建议为这个窗口增加复杂度。

## 6. 验证与回归

### 6.1 关键验证

| # | 操作 | 判定标准 |
| --- | --- | --- |
| 1 | 打印 `msgs.first.msgSeqno`、`msgs.last.msgSeqno`、`maxSeqno`、实际发出的 `ack_seqno` | 修复前 `ack_seqno == last`（最旧）；修复后 `== maxSeqno/first` |
| 2 | 只有 1 条消息的新会话 vs 有多条历史的老会话，分别"点开 → 切走 → 切回" | 修复前老会话必回弹；修复后两者都不回弹 |
| 3 | 点开会话后到**官方 Web/App** 查看该会话 | 修复前仍是未读；修复后已读（跨端验证，不依赖本 App 刷新逻辑） |
| 4 | 长按"标为已读"后切走再切回 | 修复前回弹；修复后不回弹 |
| 5 | 抓包 `update_ack` | 确认 HTTP 方法、`ack_seqno` 值、返回 `code` |

### 6.2 回归清单

- [ ] 私信列表：点开有未读的会话 → 返回 → 切 Tab 回来，未读不再出现。
- [ ] 未关注人 / 折叠 / AI / 客服二级列表：同样操作正常。
- [ ] 底栏"消息"角标：进入消息页后归零，不再回弹。
- [ ] 长按"标为已读"：成功后再刷新不回弹；断网时仍能 toast 报错。
- [ ] 向上翻页加载历史消息正常，且不再额外发 ack。
- [ ] 下拉刷新详情页仍会重新 ack 一次（幂等，无副作用）。
- [ ] 单条 `msgType=18 / msgSource=18` 的提示会话：**仍不**被误标为已读。
- [ ] 置顶 / 免打扰 / 删除会话不受影响。
- [ ] 未登录 / 登录态失效：走既有错误提示，无崩溃。

### 6.3 验收标准

1. 点开一个有多条未读的会话 → 返回 → 切走再切回 → 列表与底栏均无未读。
2. 官方客户端同步显示该会话已读。
3. 网络日志中 `ack_seqno` 等于该会话最新消息序列号。
4. 打开会话全程只增加 1 次 `update_ack`；列表点击 0 次。

## 8. 总结

- **直接原因**：详情页把本页最旧一条消息的 `msgSeqno` 当作 `ack_seqno` 发给了 `update_ack`；消息是倒序返回的，所以这个值基本没有意义。
- **次要原因**：长按"标为已读"把 `sessionDetail` 的 `ackSeqno`（已读指针）原样发回，等于空操作，但本地 UI 和成功提示造成了"已生效"的假象。
- **反复出现的机制**：列表点击只做本地乐观清除，切回消息 Tab 会强制刷新服务端数据，未读被带回。
- **修复**：详情页改发 `maxSeqno`（或 `msgs.first`）并限定只在刷新时 ack；长按"标为已读"省略 `ack_seqno`；列表点击保持乐观清除；建议顺手把 `update_ack` 对齐 POST、把 `msgSeqno` 改名 `oldestSeqno`。
- **收益**：不新增任何请求、不增加跳转延迟，同时修好列表角标、底栏角标和长按"标为已读"。

| 位置 | 实际改动 |

| `lib/http/msg.dart` | 补充 `ackSeqno` 语义注释；debug 构建下打印 `talker_id` / `ack_seqno` / 返回 `code`，便于实测核对 |

未采纳的部分及原因：

- **不传 `ack_seqno`**（§5.3）：`update_ack` 在 bilibili-API-collect（含 §7.3 引用的 commit）全库检索无条目，"留空=标到最新"无法证实，故显式传 `newestSeqno`。
- **保留 `sessionDetail` 取序号**：`GetSessionInfo` 返回的 `SessionInfo` 是否带 `max_seqno` 未经验证，而 `RspSessionMsg` 与消息本体同源，可靠性更高（`syncFetchSessionMsgs` 也可直接拿到消息兜底）。
- **GET → POST**（§5.4）：同族写接口（`removeMsg`、`setTop`、`setMsgDnd`）确实都是 POST，`api.dart` 注释也写 POST，但仍需实际抓包确认 `update_ack` 返回的 `code`；确认后再单独提交，不混入本次修复。
- **`msgSeqno` → `oldestSeqno` 已在 §5.2 一并完成，不再单列为可选。**
